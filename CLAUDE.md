# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The landing page for Moblin (moblin.app) and its companion apps. Two independent
projects live here:

- `frontend/` — a static site (SolidJS + TypeScript + Tailwind v4 + Vite), deployed to GitHub Pages.
- `backend/` — a small Rust (axum) service deployed at `https://api.moblin.app` as a Docker image. It serves the "Streamers" list and the "Erik is live on Twitch" status.

`README.md` only covers getting started; the deploy flow, App Attest and the Twitch and PayPal setup are described below and in the code.

## Commands

All checks are driven by the `justfile` at the repo root (CI runs exactly these):

```
just style          # oxfmt (frontend) + cargo fmt (backend)
just style-check
just lint           # oxlint --deny-warnings + cargo clippy --all-targets -D warnings
just spell-check    # codespell, configured in .codespellrc
just test           # cargo test (backend only; the frontend has no tests)
```

`just system-test [--device <name>] [pattern]` runs the black box system tests in `tests/` (Python, `systest`, like Moblin's `tests/`): they start the release backend and drive its API like the frontend, with the PayPal sandbox, Stripe's test mode (a new test connected account per run, set up by hand with `--interactive`) and a Moblin whose remote control streamer the tester acts as assistant for and whose Moblin Cloud connectsion it relays to the backend: the fake `tests/utils/fake_moblin.py` by default, a real device with `--device`. Not run in CI; see `tests/README.md`.

Run a single backend test: `cd backend && cargo test store::tests::list_is_capped` (tests are inline `#[cfg(test)]` modules per file).

Development needs two terminals:

```
just backend-run    # cargo run --allow-unattested, then seeds fake streamers via scripts/seed_backend.py
just frontend-run   # vite dev server; proxies /api -> localhost:8080
just backend-seed-forever [interval]   # keep posting random streamers to test live updates
```

Frontend build: `cd frontend && npm run build` (runs `tsc --noEmit` first, so type errors fail the build). Backend Docker: `just backend-docker-run`.

## Frontend architecture

- **Multi-page, no router.** Each page is its own HTML entry listed in `vite.config.ts` (`index.html`, `chat-bot/index.html`, `dashboard/index.html`, ...) with its own `src/*.tsx` entry that renders a page component. Sub pages live in a directory so GitHub Pages serves clean URLs like `/chat-bot/`. Add a page by adding all three: the HTML file, the entry, and the `rollupOptions.input` line. `404.html` is what GitHub Pages serves for unknown paths; it renders the page for `/twitch/<login>` (a signed in streamer's page; the prefix leaves room for Kick later) and a not found page otherwise. Streamers sign in and manage their page at `/dashboard/`; `/page/?streamer=<id>` shows a page by id and redirects to the dashboard without one. `/admin/` (`src/pages/Admin.tsx`) shows the operator's statistics from `GET /admin/stats` to a signed in admin, refreshed every 10 s, and is linked only from the dashboard header of an admin (`admin` in the account answer); it stays English. It opens with a status banner and a Problems table that sum the failure reasons which are our, PayPal's, Stripe's or Moblin's fault (`problems` and `problemReasons`) across songs, tips and spins; viewer mistakes and offline streamers are listed per kind below in muted rows, never counted as problems. `song-requests/index.html` only redirects old `/song-requests/` links to those.
- **Base path is dynamic.** `vite.config.ts` uses `/` when `public/CNAME` exists and `/moblin_website/` otherwise. Anything referencing a file under `public/` must go through `asset()` in `src/asset.ts`; never hardcode a leading slash in a src attribute.
- **Content lives in `src/data/`, not in components.** URLs in `links.ts`, products/features/reviews/chat-bot commands in their own files. Components in `src/components/` are one section each and are composed in order in `App.tsx`.
- **Backend access** goes through `data/backend.ts`: `/api` in dev (proxied), `links.api` in production. `data/streamers.ts` fetches the list once as a module-level SolidJS resource; `twitch.ts` polls `/twitch/live` every five minutes and falls back to "not live" on any error.
- **Theming** is Tailwind v4 `@theme` tokens in `src/index.css` (e.g. `bg-card`, `text-leaf`, `font-display`). Dark is the default; light is the same token names overridden under `prefers-color-scheme: light`. Use the tokens, not raw colors.
- **Localization** is `src/i18n.ts`: wrap every user-visible English string in `t("...")` (placeholders like `{name}` filled from the second argument) or `tRich("...", { link: <a>...</a> })` for sentences with elements in them. The English string is the key, and `scripts/translate.py` (`just machine-translate`, like Moblin's) finds them with a regex, so the first argument must be a double-quoted literal (or literals joined with `+`), never a variable. It also picks up the `<title>` of every HTML entry, which `i18n.ts` translates. Translations live in `src/locales/<code>.json`, one per language, and only the chosen one is loaded, with top-level await before any module using `t()` runs, so `t()` works at module level in `src/data/`. The language comes from the footer's picker (saved in `localStorage`, reloads the page) or the browser. Strings without a translation show in English; run `just machine-translate` after adding or changing strings. The Terms page, the admin page, the trading cards, backend error messages and the generated settings reference stay English.
- Icons are inline stroke SVGs in `components/Icon.tsx` keyed by `IconName`; platform logos on a colored disc are `BrandIcon`.

## Backend architecture

One binary, `backend/src/main.rs`, wired together from the modules below. It stops on SIGTERM or Ctrl-C by finishing the requests in flight first (axum's graceful shutdown), so a deploy never cuts a payment capture off between taking the money and saving the delivery.

- `api.rs` — the axum router. Routes: `GET /streamers`, `POST /streamers/live/challenge`, `POST /streamers/live`, `GET /twitch/live`, `GET /remote-control/streamer/{key}` (Moblin's WebSocket), `GET /pages/twitch/{login}` (the page id of a login), `GET /pages/{id}` (the page's look), `GET /pages/{id}/image` (its banner image), `GET /pages/{id}/songs` (the song price), `GET /pages/{id}/songs/queue`, `POST /pages/{id}/songs/orders`, `POST /pages/{id}/songs/orders/{order_id}/capture`, `GET /pages/{id}/tips`, `POST /pages/{id}/tips/orders`, `POST /pages/{id}/tips/orders/{order_id}/capture`, `GET /pages/{id}/spin`, `POST /pages/{id}/spin/orders`, `POST /pages/{id}/spin/orders/{order_id}/capture`, `GET /auth/twitch/login`, `GET /auth/twitch/callback`, `GET /account`, `POST /account/page`, `POST /account/devices`, `POST /account/devices/choose`, `POST /account/devices/{device}/key`, `POST /account/devices/{device}/remove`, `POST /account/settings`, `POST /account/image`, `POST /account/image/remove`, `POST /account/paypal/connect`, `POST /account/paypal/check`, `POST /account/paypal/disconnect`, `POST /account/stripe/connect`, `POST /account/stripe/check`, `POST /account/stripe/disconnect`, `POST /account/sign-out`, `GET /account/recent`, `POST /account/test/song`, `POST /account/test/tip`, `POST /account/test/spin`, `POST /paypal/webhooks`, `GET /admin/stats`. The WebSocket, live post, Twitch callback and PayPal webhook paths are registered outside this repo (in Moblin, Twitch's and PayPal's consoles) and must not be renamed. Pages are only created (automatically, on the first visit after signing in) and managed by signed in Twitch accounts; a streamer has up to 5 Moblin devices, each with its own name and Moblin Cloud key; a key is only used by Moblin's WebSocket and only leaves the backend in the signed in account (`devices`), which the streamer pastes into that device's global Moblin Cloud settings; Moblin connects to `/remote-control/streamer/{key}` under its `MOBLIN_WEBSITE_API_URL`, separately from its own remote control. The page gets its id from the key of its first device, whose device id is that same page id; later devices get random ids. `POST /account/page` returns the existing page when the account has one. Remote control sessions are per device: song requests (`find`, `status`, `songRequests`) use the page's music device and wheel spins its wheel device (`music_device`/`wheel_device`, picked with `POST /account/devices/choose`, the first device when none is picked or the picked one was removed), and the settings' `connected` is whether any device is. Song orders and their captures share the same checks (`song_and_user`, then `requested_song`, which asks Moblin to `find` the song); a completed capture queues the song (`record_capture`), answering 202. There are no free song requests. Tips need no connected streamer; a completed tip capture queues the tip (`deliveries.rs`) for Moblin. Wheel spins need Moblin's wheel (`wheel`, so a connected streamer that sent one) both to create an order and to capture it; a completed spin capture queues the spins the same way. Order requests take an optional `provider` (`paypal`, the default, or `stripe`), the public song, tip and spin answers carry the PayPal fields and `stripe` (publishable key and connected account) for whichever the streamer connected, and a Stripe order also answers its `clientSecret`. Song, tip and spin orders share `capture_order`, which refuses an order of another kind (`Item::kind`), and cancels a Stripe payment it refuses because the streamer or the wheel is gone, so the hold on the viewer's card is released. A capture moves the order through the stages in `payments.rs`: `created` to `capturing` before the provider is asked (a database that cannot be written refuses the capture with 503 `not-saved` before any money moves; two captures at once are harmless, since the provider answers the second one already captured and `record_capture` saves a capture once), then `captured` together with its delivery in one transaction (`record_capture`), back to `created` when the provider refused or the viewer had not approved, and still `capturing` while the provider reviews it, so `capturing` means the money may have been taken and only the provider can tell. When the provider's answer is lost (a transport error, a 5xx or an unreadable body, `CaptureError::Unknown`), the capture handler looks the order up at the provider at once (`settle_one`) and only answers 502 `unknown` ("did not answer. If the money was taken, the tip will still be shown.") when the lookup fails too; a retried capture of a capturing order looks it up again, and a captured one answers 202 again, so the page retries a capture on network errors and 5xx answers (three times) without ever showing an error for a payment that went through. `settle_orders` is a background task that, every minute, looks up every capturing order older than a minute (`PayPal::status`, `Stripe::status`) and queues the delivery of those the provider captured, so a pending review that completes days later, a capture whose answer was lost or a crash between the provider's answer and the database still deliver. The `/account/test/*` routes let the signed in streamer send themselves a free song, tip or wheel spin from the dashboard's Tips, Wheel of luck and Song requests sections, to check that Moblin gets them: they skip payment and need no PayPal or Stripe, but run the same Moblin checks as paid ones (`requested_song` for songs, the wheel for spins, nothing for tips, which wait in the queue for Moblin like paid tips), so songs and spins are refused with 409 `Connect Moblin first.` without a connected device; all are refused with 429 past 10 tests a minute per page (`Api::tests`, in memory), and queue a delivery under the account's name with the first suggested tip amount (5.00 without tips) or the first spin option's spins (1 without a wheel option). `GET /account/recent?kind=<song|tip|spin>` pages through the signed in streamer's captured orders of that kind, newest first (`Orders::recent`, by the `kind` column and the `orders_recent` index; captured orders are kept 30 days, so that is the whole history), `limit` of them (20 by default, at most 50) `before` the order id given, answering `items` and whether there are `more`; test deliveries are not listed. Each item has its `status`: `delivered` when its delivery is finished (or no delivery row is left), `waiting` while Moblin has not got it, `notAdded` when Moblin could not find the song, and for tips the page's `devices` with whether each `received` it (a finished tip lists only the devices that got it). The dashboard shows each kind under its section's test card (`Latest` in `Dashboard.tsx`): the first 5 when the dashboard opens, then 20 more per Show more, refreshed every 10 s (the shown ones, at most 50; older loaded ones are kept). Viewer-facing errors are full sentences the page shows as they are. `GET /admin/stats` is for the site operator: the Twitch user ids in `--admins` (env `ADMINS`, comma separated) are admins, `GET /account` answers `admin` for them and everyone else gets 403; it answers counts of accounts (total, with a page, PayPal and Stripe connected, and pages with a banner image), connected devices, unfinished orders and pending deliveries (plain column counts, no JSON is read), plus the event `counters` (`counters.rs`); unfinished orders are those not yet captured. CORS allows only `https://moblin.app` (hardcoded).
- `images.rs` — the banner image of a page. Only pro streamers (the Twitch user ids in `--pro-streamers`, env `PRO_STREAMERS`, plus admins; `GET /account` answers `pro`) may upload one, with `POST /account/image` (the file as the raw body, at most 2 MB), which the dashboard's Tip page section shows to them only. `banner` decodes a JPEG, PNG, WebP or GIF of at least 600 pixels wide and at most 4000 pixels on each side, crops it to 3:1 around the center and re-encodes it as a 1500×500 JPEG, so nothing but pixels is kept; it is saved in the `page_images` table with a version (a hash of it), answered as `image` with the page's settings and look, and served by `GET /pages/{id}/image?v=<version>` with a year long immutable cache. Counted as `imageUploads`. `POST /account/image/remove` works for everyone, and taking a streamer off `--pro-streamers` only stops new uploads; the operator deletes the row to take one down.
- `store.rs` — list of streamers, newest post first, kept in memory and saved in the `streamers` table on every change (one row per streamer, its channels with their profile, live flag and stream as JSON), so it survives restarts; pending lookups start over and the live check runs a minute after starting. It keeps the `--max-streamers` most recent posters (so a newcomer is still around when the live check runs a minute later) plus any older streamer who is still live, up to another `--max-streamers`; `streamers()` lists live streamers first, capped at `--max-streamers`. A streamer is identified by sharing any channel (platform + case-insensitive name); going live again moves to the top and keeps any already-looked-up profile and the live flag. Each listed channel carries a `Lookup` (pending with retry backoff, or done) that serializes flat into the channel JSON as `avatar`/`displayName`, plus `live` (only ever true for Twitch and Kick channels).
- `profiles.rs` — a background task that pulls the next due lookup from the store and resolves display name and avatar per platform (Twitch via Helix, YouTube via `og:` meta tags with unavatar.io fallback, Kick via `kick.rs`, its public channels API), with `--lookup-spacing` between requests.
- `app_attest.rs` — verifies Apple App Attest attestations and assertions so only the Moblin app can post live. Stateless by design: the app resends its attestation every time and the server re-verifies the chain each time, deliberately ignoring certificate validity dates. Tests use public sample vectors in `src/testdata/`.
- `challenges.rs` — one-time 32-byte challenges, 120 s lifetime, that every live post must consume.
- `remote_control.rs` — the assistant side of Moblin's remote control protocol, for song requests on the page. Moblin Cloud connects with the key in the URL and an empty password, which the backend does not check. Serde types mirror Swift's synthesized `Codable` (`{"ping":{}}`, optional fields omitted), and must match `Moblin/RemoteControl/RemoteControl.swift` in the Moblin repo. Moblin pushes its wheel (the wheel of luck widget picked in Moblin's Moblin Cloud settings) as a `wheelOfLuck` event on connect and on every change; it is kept with the session and served by `GET /pages/{id}/spin` as `wheel` for the page to draw, next to `connected`, so the page can tell a streamer who is offline from one who picked no wheel (whose spin orders are refused with 409). It also pushes `songRequests` (`enabled`, the Song requests toggle in the same settings) on connect and on every change; while it is off (it is on until Moblin says otherwise), song orders and song captures are refused with 409 and `GET /pages/{id}/songs/queue` answers `songRequests: false`, so the page says songs can't be added right now but still shows the queue. Requests sent are `spinWheelOfLuck` (viewer name, message, number of spins and `requestId`) and `tip` (viewer name, message, amount as a string like `7.00`, currency and `requestId`), both answered `ok` without data and deduplicated by Moblin on `requestId`, and `music`: `status`, `find` (is a song on the streamer's Apple Music, asked before payment) and `add` (with the viewer's optional `message`, which Moblin does not read yet, and an optional `requestId`, kept on the song in Moblin's playlist; Moblin answers `ok` without adding again when a playlist song already has it, and `error` when it could not add it). Song requests must be Apple Music song links, sent as `https://music.apple.com/song/<id>?i=<id>`.
- `database.rs` — the SQLite database (`rusqlite`, SQLite bundled) at `--database`, in memory without it, shared by `Store`, `Accounts`, `Pages`, `Orders`, `Deliveries` and `Counters` behind one mutex. Tables are created with `CREATE TABLE IF NOT EXISTS` on start.
- `counters.rs` — event counters for the admin page, one row per name and UTC day in the `counters` table, read back as today, last 7 days and all time. Measurement points come in pairs, `<name>` for successes and `<name>Failed:<reason>` for failures, where the reason is the `reason` slug every `Failure` in `api.rs` carries (`counted` does the bumping), which the admin page lists as one plain row per reason under the success row, always showing the reasons each code path can produce (`failures` per event in `Admin.tsx`, labels in `reasonLabels`) plus any unexpected one that occurred: Moblin's WebSocket connecting with a known or unknown key (`moblinConnections`), created orders and captured payments (`songOrders`, `songPayments` and so on per `Item::kind`, any refusal or provider error counting as failed), and in `deliveries.rs` a delivery that reached every device (`songDeliveries`, `tipDeliveries`, `spinDeliveries`) or that Moblin could not find or refused (`...DeliveriesFailed`, once per delivery and reason). The free `counters::bump` takes a connection, for callers already holding the database lock.
- `pages.rs` — per streamer page settings (`Pages`), keyed by the public id: the one currency of all its payments (USD by default, set in the dashboard's Payments section; changing it while a paid feature is on needs PayPal or Stripe connected), an optional paywall (price in hundredths, for every started 5 minutes of the song's duration from Moblin's `find`, so long songs cost more and always play in full; song requests are on exactly when it is set), optional tips (one to five suggested amounts in hundredths), an optional spin wheel (one to five options of a number of spins and its price) and the look of the page (headline up to 60 characters, message up to 300, accent color from a fixed list whose CSS lives in `index.css` as `[data-accent]` overrides of the moss/leaf tokens, and font from a fixed list, `[data-font]` overrides of `--font-display`/`--font-body` whose Google Fonts `loadFonts` adds only when used). `GET /pages/{id}` returns the look with the name, avatar and banner image version (`images.rs`). Saved as JSON in the `pages` table on every change.
- `auth.rs` — streamer sign in with Twitch only (OAuth authorization code), with one-time states that last 10 minutes and must match the `moblin_sign_in_state` cookie set by `GET /auth/twitch/login`, so a callback URL only works in the browser that started the sign in. Sessions are `<twitch user id>:<generation>:<issued>` signed with HMAC-SHA256 under `--session-secret` (random without it), 30 days, sent as a bearer token. A session is only accepted while its generation matches the account's `sessions` counter, which signing out increments; starting to connect PayPal (`POST /account/paypal/connect`) needs a session issued in the last 10 minutes. The Twitch URLs are fields of `OAuthApp` so tests can point them at a local server.
- `accounts.rs` — accounts keyed by Twitch user id, each with a display name and Twitch profile image (shown on the page), the login that gives the page its `/twitch/<login>` address (taken from other accounts on sign in, after renames), its page: a public id fixed at creation, its devices (saved as JSON in `page_devices`; `POST /account/devices/{device}/key` replaces a device's key and the WebSocket route only accepts current keys, via `device_of_key`; older databases have their single `page_key` dropped on start, so those streamers add their devices again) and the chosen music and wheel devices, and its PayPal: the merchant ID every paid feature of the page pays (`merchant_of`) and the tracking ID of an unfinished onboarding, and its Stripe connected account with whether it takes payments yet (`stripe_of`, only ready accounts). The merchant ID only ever comes from PayPal's seller onboarding (Partner Referrals): `POST /account/paypal/connect` creates a referral and answers PayPal's sign up link, and `POST /account/paypal/check` looks the tracking ID up with PayPal and connects the merchant ID once it can receive payments, has a confirmed email and granted our app third-party permissions; the return URL's parameters are never trusted. `POST /paypal/webhooks` (verified with PayPal's verify webhook signature API under `--paypal-webhook-id`) connects pending onboardings on `MERCHANT.ONBOARDING.COMPLETED` through the same `finish_onboarding` checks and disconnects merchants on `MERCHANT.PARTNER-CONSENT.REVOKED`; `POST /account/paypal/disconnect` forgets the merchant ID and any unfinished onboarding. Paid features can only be turned on or changed while PayPal or Stripe is connected. Saved in the `accounts` table, whose Stripe columns are added to older databases on start.
- `paypal.rs` — PayPal partner client: seller onboarding (`referral`, `seller`, which need the partner's merchant ID `--paypal-partner-id`; `--paypal-attribution-id` is the BN code sent with every request), webhook verification and Orders v2, created and captured for the streamer with an unsigned `PayPal-Auth-Assertion` JWT naming their merchant ID, for paid song requests, tips and wheel spins (an order's `Item` is a song, a tip with its message or a spin purchase with its number of spins and message): orders name the streamer's PayPal merchant ID as payee so money goes straight to them (never the email: PayPal no longer accepts emails as the SDK's `merchant-id`, and it would be public). A completed capture whose amount matches queues the song; a pending one (PayPal still reviewing it) is settled later by `settle_orders`, which asks `status` (GET the order).
- `stripe.rs` — Stripe Connect platform client, the alternative to PayPal. Streamers get a connected account (Accounts v2 API, full Stripe Dashboard, Stripe collects fees and losses) created on the first `POST /account/stripe/connect` in the country the streamer picks (`stripe::COUNTRIES`, the countries Stripe takes sign ups from, also listed in the frontend; Stripe can't change it later), which answers a Stripe-hosted onboarding link back to `/dashboard/?stripe`; `POST /account/stripe/check` marks it ready once its `card_payments` capability is active. Payments are direct charges on the connected account (`Stripe-Account` header): a PaymentIntent (v1 API) with `capture_method=manual`, no redirect payment methods and no application fee, confirmed in the browser with the client secret and captured by the backend, like a PayPal order. On the page, "Pay with Stripe" creates the order first (so the viewer sees the final price, which for songs depends on the song) and then shows Stripe's Payment Element; changing the form closes it. `status` (GET the PaymentIntent) settles payments whose capture answer was lost. There are no Stripe webhooks; a revoked account only fails new payments until the streamer checks again. `--stripe-secret-key` and `--stripe-publishable-key`; a test mode key takes test payments.
- `payments.rs` — what is provider neutral about payments: the order (`Item`, `Order` with its `Payee`, a PayPal merchant ID or a Stripe account, and its description), `CaptureError` (`NotApproved`, `AlreadyCaptured`, `Pending`, `Refused` when the provider definitely said no, `Unknown` when its answer was lost), `PaymentStatus` (what a lookup at the provider says: captured, pending, not captured or gone) and `Orders`, every order in the `orders` table with its `Stage` (`created`, `capturing`, `captured`) and the order as JSON, so a restart loses no payment: `start_order` inserts after creating the provider's order (refusing the order with 503 `not-saved` if that fails), `transition` is a compare-and-set between stages, `captured` runs the stage change and the delivery insert in one transaction, `unsettled` lists the capturing orders older than a given age for `settle_orders`, `expire` drops created orders after three hours (`settle_orders` then cancels their Stripe payments, so a viewer whose capture never reached the backend gets the hold on their card released), `make_room` refuses new ones past 10000 unfinished, `captured` does nothing for an order already captured and otherwise counts `<kind>Payments` in the same transaction as the delivery, so a payment is counted once however it was found, and `prune` gives unsettled orders up and forgets captured ones after 30 days.
- `deliveries.rs` — at least once delivery to Moblin of paid songs, tips and wheel spins, saved in the `deliveries` table. Deliveries are kept per page and their devices picked when delivering: songs go to the music device, spins to the wheel device and tips to every device of the page, tracked in `delivered` so each device gets a tip once. A delivery every device got is marked `finished` and kept 30 days, so the dashboard can tell which devices got a tip. Test deliveries (`add_test`) are marked with their kind in `test`, and only the 5 newest per page and kind are kept. A background task delivers them whenever a device connects, after a request and every 10 s, each connected device concurrently, by sending `add`, `tip` or `spinWheelOfLuck` with the request id (random, or the PayPal order id) as `requestId` until Moblin answers `ok`; Moblin's own dedup on `requestId` makes the retries safe. A song request is always delivered as a song, never as anything else. A song Moblin answers it can't find (`songNotFound`) is final: the delivery stays in the table with `failure` set to `not-found`, is not sent again, shows as `notAdded` on the dashboard so the streamer can add it by hand or refund, and is forgotten after 30 days. Any other Moblin `error` (Apple Music not authorized, playlist not loaded, a failed search) is temporary and retried; `failure` records the latest reason so each failure is counted once per delivery and reason. A delivery waits in the table until a device gets it and is only given up after 7 days (the one way a paid request is allowed to fail), counted as `songExpiries`, `tipExpiries` or `spinExpiries` when no device got it.
- `twitch.rs` / `live.rs` / `live_status.rs` — Helix client with a cached app access token; a once-per-minute cache of whether the featured channel is live; and a background task that checks which listed channels are live every five minutes and one minute after a live post: all Twitch channels in one streams request, Kick channels one by one with `--lookup-spacing` between them.

Everything optional degrades rather than fails: without Twitch credentials, Twitch profiles come back empty and `/twitch/live` answers 503. `--allow-unattested` disables App Attest and `--fake-twitch-sign-in` signs in as a made-up Twitch user without contacting Twitch, both for local development only (`just backend-run` passes both, and `--admins fake-streamer` so the default fake user is an admin, and so pro).

## Conventions

- **Do not write comments or docstrings.**
- **Magic numbers are fine, and often preferred, when used in a single place.** Do not hoist a literal
  into a named constant just because it is a literal — only name it when the same value is used in more
  than one place.
- Rust edition 2024 (let-chains are used). Clippy warnings are errors in CI.
- The `/streamers/live` request shape (`channels`, `challenge`, `keyId`, `attestation`, `attestationChallenge`, header `moblin-assertion`) is a contract with the Moblin iOS app; changing it requires an app change too.
- Streamers appear in the list only if they opted in inside the Moblin app. Site copy must not imply that everyone who goes live is listed.

## Reporting

- Never mention styling or formatting changes (oxfmt, cargo fmt output) in summaries, reviews or commit
  messages.
