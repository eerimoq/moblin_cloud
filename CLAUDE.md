# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The landing page for Moblin (moblin.app) and its companion apps. Two independent
projects live here:

- `frontend/` — a static site (SolidJS + TypeScript + Tailwind v4 + Vite), deployed to GitHub Pages.
- `backend/` — a small Rust (axum) service deployed at `https://api.moblin.app` as a Docker image. It serves the "Streamers" list and the "Erik is live on Twitch" status.

`README.md` only covers getting started; the deploy flow, App Attest and the Twitch and PayPal setup are described below and in the code.

## Commands

All checks are driven by the `justfile` at the repo root (CI runs exactly these):

```
just style          # oxfmt (frontend) + cargo fmt (backend)
just style-check
just lint           # oxlint --deny-warnings + cargo clippy --all-targets -D warnings
just spell-check    # codespell, configured in .codespellrc
just test           # cargo test (backend only; the frontend has no tests)
```

`just system-test [--device <name>] [pattern]` runs the black box system tests in `tests/` (Python, `systest`, like Moblin's `tests/`): they start the release backend and drive its API like the frontend, with the PayPal sandbox, Stripe's test mode (a new test connected account per run, set up by hand with `--interactive`) and a Moblin whose remote control streamer the tester acts as assistant for and whose Moblin Cloud connectsion it relays to the backend: the fake `tests/utils/fake_moblin.py` by default, a real device with `--device`. Not run in CI; see `tests/README.md`.

Run a single backend test: `cd backend && cargo test store::tests::list_is_capped` (tests are inline `#[cfg(test)]` modules per file).

Development needs two terminals:

```
just backend-run    # cargo run --allow-unattested, then seeds fake streamers via scripts/seed_backend.py
just frontend-run   # vite dev server; proxies /api -> localhost:8080
just backend-seed-forever [interval]   # keep posting random streamers to test live updates
```

Frontend build: `cd frontend && npm run build` (runs `tsc --noEmit` first, so type errors fail the build). Backend Docker: `just backend-docker-run`.

## Frontend architecture

- **Multi-page, no router.** Each page is its own HTML entry listed in `vite.config.ts` (`index.html`, `chat-bot/index.html`, `dashboard/index.html`, ...) with its own `src/*.tsx` entry that renders a page component. Sub pages live in a directory so GitHub Pages serves clean URLs like `/chat-bot/`. Add a page by adding all three: the HTML file, the entry, and the `rollupOptions.input` line. `404.html` is what GitHub Pages serves for unknown paths; it renders the page for `/twitch/<login>` (a signed in streamer's page; the prefix leaves room for Kick later) and a not found page otherwise. Streamers sign in and manage their page at `/dashboard/`; `/page/?streamer=<id>` shows a page by id and redirects to the dashboard without one. `song-requests/index.html` only redirects old `/song-requests/` links to those.
- **Base path is dynamic.** `vite.config.ts` uses `/` when `public/CNAME` exists and `/moblin_website/` otherwise. Anything referencing a file under `public/` must go through `asset()` in `src/asset.ts`; never hardcode a leading slash in a src attribute.
- **Content lives in `src/data/`, not in components.** URLs in `links.ts`, products/features/reviews/chat-bot commands in their own files. Components in `src/components/` are one section each and are composed in order in `App.tsx`.
- **Backend access** goes through `data/backend.ts`: `/api` in dev (proxied), `links.api` in production. `data/streamers.ts` fetches the list once as a module-level SolidJS resource; `twitch.ts` polls `/twitch/live` every five minutes and falls back to "not live" on any error.
- **Theming** is Tailwind v4 `@theme` tokens in `src/index.css` (e.g. `bg-card`, `text-leaf`, `font-display`). Dark is the default; light is the same token names overridden under `prefers-color-scheme: light`. Use the tokens, not raw colors.
- **Localization** is `src/i18n.ts`: wrap every user-visible English string in `t("...")` (placeholders like `{name}` filled from the second argument) or `tRich("...", { link: <a>...</a> })` for sentences with elements in them. The English string is the key, and `scripts/translate.py` (`just machine-translate`, like Moblin's) finds them with a regex, so the first argument must be a double-quoted literal (or literals joined with `+`), never a variable. It also picks up the `<title>` of every HTML entry, which `i18n.ts` translates. Translations live in `src/locales/<code>.json`, one per language, and only the chosen one is loaded, with top-level await before any module using `t()` runs, so `t()` works at module level in `src/data/`. The language comes from the footer's picker (saved in `localStorage`, reloads the page) or the browser. Strings without a translation show in English; run `just machine-translate` after adding or changing strings. The Terms page, the trading cards, backend error messages and the generated settings reference stay English.
- Icons are inline stroke SVGs in `components/Icon.tsx` keyed by `IconName`; platform logos on a colored disc are `BrandIcon`.

## Backend architecture

One binary, `backend/src/main.rs`, wired together from:

- `api.rs` — the axum router. Routes: `GET /streamers`, `POST /streamers/live/challenge`, `POST /streamers/live`, `GET /twitch/live`, `GET /remote-control/streamer/{key}` (Moblin's WebSocket), `GET /pages/twitch/{login}` (the page id of a login), `GET /pages/{id}` (the page's look), `GET /pages/{id}/songs` (the song price), `GET /pages/{id}/songs/queue`, `POST /pages/{id}/songs/orders`, `POST /pages/{id}/songs/orders/{order_id}/capture`, `GET /pages/{id}/tips`, `POST /pages/{id}/tips/orders`, `POST /pages/{id}/tips/orders/{order_id}/capture`, `GET /pages/{id}/spin`, `POST /pages/{id}/spin/orders`, `POST /pages/{id}/spin/orders/{order_id}/capture`, `GET /auth/twitch/login`, `GET /auth/twitch/callback`, `GET /account`, `POST /account/page`, `POST /account/devices`, `POST /account/devices/choose`, `POST /account/devices/{device}/key`, `POST /account/devices/{device}/remove`, `POST /account/settings`, `POST /account/paypal/connect`, `POST /account/paypal/check`, `POST /account/paypal/disconnect`, `POST /account/stripe/connect`, `POST /account/stripe/check`, `POST /account/stripe/disconnect`, `POST /account/sign-out`, `POST /account/test/song`, `POST /account/test/tip`, `POST /account/test/spin`, `POST /paypal/webhooks`. The WebSocket, live post, Twitch callback and PayPal webhook paths are registered outside this repo (in Moblin, Twitch's and PayPal's consoles) and must not be renamed. Pages are only created (automatically, on the first visit after signing in) and managed by signed in Twitch accounts; a streamer has up to 5 Moblin devices, each with its own name and Moblin Cloud key; a key is only used by Moblin's WebSocket and only leaves the backend in the signed in account (`devices`), which the streamer pastes into that device's global Moblin Cloud settings; Moblin connects to `/remote-control/streamer/{key}` under its `MOBLIN_WEBSITE_API_URL`, separately from its own remote control. The page gets its id from the key of its first device, whose device id is that same page id; later devices get random ids. `POST /account/page` returns the existing page when the account has one. Remote control sessions are per device: song requests (`find`, `status`, `songRequests`) use the page's music device and wheel spins its wheel device (`music_device`/`wheel_device`, picked with `POST /account/devices/choose`, the first device when none is picked or the picked one was removed), and the settings' `connected` is whether any device is. Song orders and their captures share the same checks (`song_and_user`, then `requested_song`, which asks Moblin to `find` the song); a completed capture ends in `queue`, answering 202. There are no free song requests. Tips need no connected streamer; a completed tip capture queues the tip (`deliveries.rs`) for Moblin. Wheel spins need Moblin's wheel (`wheel`, so a connected streamer that sent one) both to create an order and to capture it; a completed spin capture queues the spins the same way. Order requests take an optional `provider` (`paypal`, the default, or `stripe`), the public song, tip and spin answers carry the PayPal fields and `stripe` (publishable key and connected account) for whichever the streamer connected, and a Stripe order also answers its `clientSecret`. Song, tip and spin orders share `capture`, which refuses an order of another kind (`Item::kind`), and cancels a Stripe payment it refuses because the streamer or the wheel is gone, so the hold on the viewer's card is released. The `/account/test/*` routes let the signed in streamer send themselves a free song, tip or wheel spin from the dashboard's Tips, Wheel of luck and Song requests sections, to check that Moblin gets them: they skip payment and need no PayPal or Stripe, but run the same Moblin checks (a connected device, `requested_song` for songs, the wheel for spins), are refused with 409 `Connect Moblin first.` without a connected device, and queue a delivery under the account's name with the first suggested tip amount (5.00 without tips) or the first spin option's spins (1 without a wheel option). Viewer-facing errors are full sentences the page shows as they are. CORS allows only `https://moblin.app` (hardcoded).
- `store.rs` — list of streamers, newest post first, kept in memory and saved in the `streamers` table on every change (one row per streamer, its channels with their profile, live flag and stream as JSON), so it survives restarts; pending lookups start over and the live check runs a minute after starting. It keeps the `--max-streamers` most recent posters (so a newcomer is still around when the live check runs a minute later) plus any older streamer who is still live, up to another `--max-streamers`; `streamers()` lists live streamers first, capped at `--max-streamers`. A streamer is identified by sharing any channel (platform + case-insensitive name); going live again moves to the top and keeps any already-looked-up profile and the live flag. Each listed channel carries a `Lookup` (pending with retry backoff, or done) that serializes flat into the channel JSON as `avatar`/`displayName`, plus `live` (only ever true for Twitch and Kick channels).
- `profiles.rs` — a background task that pulls the next due lookup from the store and resolves display name and avatar per platform (Twitch via Helix, YouTube via `og:` meta tags with unavatar.io fallback, Kick via `kick.rs`, its public channels API), with `--lookup-spacing` between requests.
- `app_attest.rs` — verifies Apple App Attest attestations and assertions so only the Moblin app can post live. Stateless by design: the app resends its attestation every time and the server re-verifies the chain each time, deliberately ignoring certificate validity dates. Tests use public sample vectors in `src/testdata/`.
- `challenges.rs` — one-time 32-byte challenges, 120 s lifetime, that every live post must consume.
- `remote_control.rs` — the assistant side of Moblin's remote control protocol, for song requests on the page. Moblin Cloud connects with the key in the URL and an empty password, which the backend does not check. Serde types mirror Swift's synthesized `Codable` (`{"ping":{}}`, optional fields omitted), and must match `Moblin/RemoteControl/RemoteControl.swift` in the Moblin repo. Moblin pushes its wheel (the wheel of luck widget picked in Moblin's Moblin Cloud settings) as a `wheelOfLuck` event on connect and on every change; it is kept with the session and served by `GET /pages/{id}/spin` as `wheel` for the page to draw, next to `connected`, so the page can tell a streamer who is offline from one who picked no wheel (whose spin orders are refused with 409). It also pushes `songRequests` (`enabled`, the Song requests toggle in the same settings) on connect and on every change; while it is off (it is on until Moblin says otherwise), song orders and song captures are refused with 409 and `GET /pages/{id}/songs/queue` answers `songRequests: false`, so the page says songs can't be added right now but still shows the queue. Requests sent are `spinWheelOfLuck` (viewer name, message, number of spins and `requestId`) and `tip` (viewer name, message, amount as a string like `7.00`, currency and `requestId`), both answered `ok` without data and deduplicated by Moblin on `requestId`, and `music`: `status`, `find` (is a song on the streamer's Apple Music, asked before payment) and `add` (with an optional `requestId`, kept on the song in Moblin's playlist; Moblin answers `ok` without adding again when a playlist song already has it, and `error` when it could not add it). Song requests must be Apple Music song links, sent as `https://music.apple.com/song/<id>?i=<id>`.
- `database.rs` — the SQLite database (`rusqlite`, SQLite bundled) at `--database`, in memory without it, shared by `Store`, `Accounts`, `Pages` and `Deliveries` behind one mutex. Tables are created with `CREATE TABLE IF NOT EXISTS` on start.
- `pages.rs` — per streamer page settings (`Pages`), keyed by the public id: the one currency of all its payments (USD by default, set in the dashboard's Payments section; changing it while a paid feature is on needs PayPal or Stripe connected), an optional paywall (price in hundredths, for every started 5 minutes of the song's duration from Moblin's `find`, so long songs cost more and always play in full; song requests are on exactly when it is set), optional tips (one to five suggested amounts in hundredths), an optional spin wheel (one to five options of a number of spins and its price) and the look of the page (headline up to 60 characters, message up to 300, accent color from a fixed list whose CSS lives in `index.css` as `[data-accent]` overrides of the moss/leaf tokens). `GET /pages/{id}` returns the look with the name and avatar. Saved as JSON in the `pages` table on every change.
- `auth.rs` — streamer sign in with Twitch only (OAuth authorization code), with one-time states that last 10 minutes and must match the `moblin_sign_in_state` cookie set by `GET /auth/twitch/login`, so a callback URL only works in the browser that started the sign in. Sessions are `<twitch user id>:<generation>:<issued>` signed with HMAC-SHA256 under `--session-secret` (random without it), 30 days, sent as a bearer token. A session is only accepted while its generation matches the account's `sessions` counter, which signing out increments; starting to connect PayPal (`POST /account/paypal/connect`) needs a session issued in the last 10 minutes. The Twitch URLs are fields of `OAuthApp` so tests can point them at a local server.
- `accounts.rs` — accounts keyed by Twitch user id, each with a display name and Twitch profile image (shown on the page), the login that gives the page its `/twitch/<login>` address (taken from other accounts on sign in, after renames), its page: a public id fixed at creation, its devices (saved as JSON in `page_devices`; `POST /account/devices/{device}/key` replaces a device's key and the WebSocket route only accepts current keys, via `device_of_key`; older databases have their single `page_key` dropped on start, so those streamers add their devices again) and the chosen music and wheel devices, and its PayPal: the merchant ID every paid feature of the page pays (`merchant_of`) and the tracking ID of an unfinished onboarding, and its Stripe connected account with whether it takes payments yet (`stripe_of`, only ready accounts). The merchant ID only ever comes from PayPal's seller onboarding (Partner Referrals): `POST /account/paypal/connect` creates a referral and answers PayPal's sign up link, and `POST /account/paypal/check` looks the tracking ID up with PayPal and connects the merchant ID once it can receive payments, has a confirmed email and granted our app third-party permissions; the return URL's parameters are never trusted. `POST /paypal/webhooks` (verified with PayPal's verify webhook signature API under `--paypal-webhook-id`) connects pending onboardings on `MERCHANT.ONBOARDING.COMPLETED` through the same `finish_onboarding` checks and disconnects merchants on `MERCHANT.PARTNER-CONSENT.REVOKED`; `POST /account/paypal/disconnect` forgets the merchant ID and any unfinished onboarding. Paid features can only be turned on or changed while PayPal or Stripe is connected. Saved in the `accounts` table, whose Stripe columns are added to older databases on start.
- `paypal.rs` — PayPal partner client: seller onboarding (`referral`, `seller`, which need the partner's merchant ID `--paypal-partner-id`; `--paypal-attribution-id` is the BN code sent with every request), webhook verification and Orders v2, created and captured for the streamer with an unsigned `PayPal-Auth-Assertion` JWT naming their merchant ID, for paid song requests, tips and wheel spins (an order's `Item` is a song, a tip with its message or a spin purchase with its number of spins and message): orders name the streamer's PayPal merchant ID as payee so money goes straight to them (never the email: PayPal no longer accepts emails as the SDK's `merchant-id`, and it would be public). A completed capture whose amount matches queues the song; a pending one (PayPal still reviewing it) does not.
- `stripe.rs` — Stripe Connect platform client, the alternative to PayPal. Streamers get a connected account (Accounts v2 API, full Stripe Dashboard, Stripe collects fees and losses) created on the first `POST /account/stripe/connect` in the country the streamer picks (`stripe::COUNTRIES`, the countries Stripe takes sign ups from, also listed in the frontend; Stripe can't change it later), which answers a Stripe-hosted onboarding link back to `/dashboard/?stripe`; `POST /account/stripe/check` marks it ready once its `card_payments` capability is active. Payments are direct charges on the connected account (`Stripe-Account` header): a PaymentIntent with `capture_method=manual` and no redirect payment methods, confirmed in the browser with the client secret and captured by the backend, like a PayPal order. On the page, "Pay with card" creates the order first (so the viewer sees the final price, which for songs depends on the song) and then shows Stripe's Payment Element; changing the form closes it. There are no Stripe webhooks; a revoked account only fails new payments until the streamer checks again. `--stripe-secret-key` and `--stripe-publishable-key`; a test mode key takes test payments.
- `payments.rs` — what is provider neutral about payments: the order (`Item`, `Order` with its `Payee`, a PayPal merchant ID or a Stripe account, and its description), `CaptureError`, and `Orders`, the pending orders (song, user, price) kept in memory for three hours, which `api.rs` adds to after creating an order and removes from once the provider's capture answer is final.
- `deliveries.rs` — at least once delivery to Moblin of paid songs, tips and wheel spins, saved in the `deliveries` table. Deliveries are kept per page and their devices picked when delivering: songs go to the music device, spins to the wheel device and tips to every device of the page, tracked in `delivered` so each device gets a tip once. A background task delivers them whenever a device connects, after a request and every 10 s, each connected device concurrently, by sending `add`, `tip` or `spinWheelOfLuck` with the request id (random, or the PayPal order id) as `requestId` until Moblin answers `ok`; Moblin's own dedup on `requestId` makes the retries safe. Drops songs Moblin can't find; gives up after 7 days.
- `twitch.rs` / `live.rs` / `live_status.rs` — Helix client with a cached app access token; a once-per-minute cache of whether the featured channel is live; and a background task that checks which listed channels are live every five minutes and one minute after a live post: all Twitch channels in one streams request, Kick channels one by one with `--lookup-spacing` between them.

Everything optional degrades rather than fails: without Twitch credentials, Twitch profiles come back empty and `/twitch/live` answers 503. `--allow-unattested` disables App Attest and `--fake-twitch-sign-in` signs in as a made-up Twitch user without contacting Twitch, both for local development only (`just backend-run` passes both).

## Conventions

- **Do not write comments or docstrings.**
- **Magic numbers are fine, and often preferred, when used in a single place.** Do not hoist a literal
  into a named constant just because it is a literal — only name it when the same value is used in more
  than one place.
- Rust edition 2024 (let-chains are used). Clippy warnings are errors in CI.
- The `/streamers/live` request shape (`channels`, `challenge`, `keyId`, `attestation`, `attestationChallenge`, header `moblin-assertion`) is a contract with the Moblin iOS app; changing it requires an app change too.
- Streamers appear in the list only if they opted in inside the Moblin app. Site copy must not imply that everyone who goes live is listed.
