# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Moblin Cloud (cloud.moblin.app): the streamers' tip pages, where viewers tip them and spin their
wheel of luck, the dashboard where they manage them, and the connection to their Moblin devices.
The landing page for Moblin (moblin.app) is its own repository, `moblin_website`. Two independent
projects live here:

- `frontend/` — a static site (SolidJS + TypeScript + Tailwind v4 + Vite), deployed to GitHub Pages.
- `backend/` — a small Rust (axum) service deployed at `https://cloud-api.moblin.app` as a Docker image. It serves the pages, the dashboard and Moblin's Moblin Cloud WebSocket.

`deploy/` runs a copy of both on one server with Docker Compose, from the images the deploy workflow publishes on every tag: the backend and the frontend (`frontend/Dockerfile`, the built site in Caddy on plain HTTP, which proxies `/api` to the backend at `BACKEND_HOST`, `backend:8080` by default, `frontend/Caddyfile`, behind the stock Caddy image, which gets the certificate and serves HTTPS); see its README.

`README.md` only covers getting started; the deploy flow, App Attest and the Twitch and PayPal setup are described below and in the code.

## Commands

All checks are driven by the `justfile` at the repo root (CI runs exactly these):

```
just style          # oxfmt (frontend) + cargo fmt (backend)
just style-check
just lint           # oxlint --deny-warnings + cargo clippy --all-targets -D warnings
just spell-check    # codespell, configured in .codespellrc
just test           # cargo test (backend only; the frontend has no tests)
```

`just system-test [--device <name>] [pattern]` runs the black box system tests in `tests/` (Python, `systest`, like Moblin's `tests/`): they start the release backend and drive its API like the frontend, with the fake PayPal and Stripe in `tests/utils/fake_paypal.py` and `tests/utils/fake_stripe.py` (stdlib only, started once per run so their orders survive backend restarts; the backend is pointed at them with `--paypal-url` and `--stripe-url`, which are for the tests only, and a PayPal URL other than the live one is the sandbox) and a Moblin whose remote control streamer the tester acts as assistant for and whose Moblin Cloud connectsion it relays to the backend: the fake `tests/utils/fake_moblin.py` by default (it pushes a made-up top right status every second between `startStatus` and `stopStatus`, with random bitrate and bonding numbers, answers `getStatus` and `getSettings` (from the made-up settings in `tests/utils/fake_moblin_database.py`), keeps the state the controls change, filters and macros included, and, between `startPreview` and `stopPreview`, a PNG preview frame every second drawn from its scene, zoom, torch and filters), a real device with `--device`. `just dev-fake-moblin` connects the fake to a running `just dev-backend` as the admin user's Moblin (with `--key` taken from the dev database, so sign in as `admin` once first). Not run in CI; see `tests/README.md`.

Run a single backend test: `cd backend && cargo test payments::tests::orders_survive_restarts` (tests are inline `#[cfg(test)]` modules per file; the API's are under each `api/*.rs`, e.g. `cargo test api::tips::tests`, sharing `start_api_with`, the socket helpers and the fake PayPal, Stripe, Twitch and Kick servers in `api/test_utils.rs` and `api/test_utils/`).

`just dev` starts everything in one terminal: `dev-backend`, `dev-frontend`, then signs in as `admin` on the fake Twitch and runs `dev-fake-moblin`. The development recipes are all in the `dev` group of `just --list`. Otherwise development needs two terminals:

```
just dev-backend    # starts the fake Twitch and Kick, then cargo run --allow-unattested with backend/database.sqlite
just dev-frontend   # vite dev server; proxies /api -> localhost:8080
```

Frontend build: `cd frontend && npm run build` (runs `tsc --noEmit` first, so type errors fail the build).

## Frontend architecture

- **Multi-page, no router.** Each page is its own HTML entry listed in `vite.config.ts` (`dashboard/index.html`, `page/index.html`, ...) with its own `src/*.tsx` entry that renders a page component. Sub pages live in a directory so GitHub Pages serves clean URLs like `/account/`. The dashboard is `index.html`, at the site root (`pages.dashboard`); `dashboard/index.html` renders it too, for the backend's sign in, PayPal and Stripe redirects and old links, and `src/dashboard.tsx` replaces `/dashboard/` with `/` in the address bar, while an assisted streamer's dashboard stays under `/dashboard/<platform>/<login>` (`pages.assisted`), since `/<platform>/<login>` is their tip page. Add a page by adding all three: the HTML file, the entry, and the `rollupOptions.input` line. `404.html` is what GitHub Pages serves for unknown paths; it renders the page for `/twitch/<login>` and `/kick/<login>` (a signed in streamer's page under the login of that linked platform, showing that platform's name, avatar and channel link; both addresses show the same page and settings), the dashboard for `/dashboard/twitch/<login>` (an assisted streamer's dashboard) `/device/<page id>/<device id>` (a device's remote control, in the dashboard) and `/monitor/<page id>` (the monitor, in the dashboard) and a not found page otherwise. Streamers sign in and manage their page at `/`; `/page/?streamer=<id>` shows a page by id and redirects to the dashboard without one. The page header shows a link to the dashboard when the browser holds a streamer session (`readSession`) whose account owns the page (its `settings.id`) or assists it (`assisting`), to `/dashboard/<platform>/<login>` for an assistant under the platform the page is shown on (`dashboardLink` in `pages/Page.tsx`). Admin (`AdminView` in `src/pages/Admin.tsx`, loaded lazily) shows the operator's statistics from `GET /admin/stats/events` (the `stats` that `GET /admin/stats` answers, pushed every 2 s) in the dashboard shell at `/admin/` (`admin/index.html` renders the dashboard, which reads the path), picked in the page picker only by an admin (`admin` in the account answer; anyone else is sent to the dashboard) and kept whatever streamer is picked, since it is not per page (picking a streamer while it is shown opens their dashboard); it stays English. - **Base path is dynamic.** `vite.config.ts` uses `/` when `public/CNAME` exists and `/moblin_cloud/` otherwise. Anything referencing a file under `public/` must go through `asset()` in `src/asset.ts`; never hardcode a leading slash in a src attribute.
- **Content lives in `src/data/`, not in components.** URLs in `links.ts` (the Moblin website's as `links.website` and `links.docs`), effects, Moblin's settings and the remote control types in their own files. Components in `src/components/` are the parts the pages are composed of.
- **Backend access** goes through `data/backend.ts`: `links.api`: `backendUrl` in `config.js`, a plain script every HTML entry loads before its module, so the backend is configured at deploy time, not build time: `public/config.js` has `/api` (proxied to the backend by the dev server, and by Caddy in the frontend image), and the Deploy frontend workflow overwrites it in `dist/` with the repository variable `BACKEND_URL` (`https://cloud-api.moblin.app` for cloud.moblin.app), which GitHub Pages needs since it can't proxy `/api`. A new HTML entry needs the `<script src="/config.js"></script>` too. Nothing is polled: everything that changes on the backend is pushed as server-sent events read with `subscribe` in `src/sse.ts` (closed while the tab is hidden, so a hidden page costs nothing, and not retried after a 4xx until the tab is shown again). The dashboard (for its sections and the page picker alike) and the tip page use change streams that only name what changed (`subscribeChanges`: each event name maps to a refetch through the normal GET routes, and every refetch runs again when the stream reopens, since events may have been missed while it was closed): `GET /account/pages/{id}/events` for the owner and assistants (`account` refetches the account, `recent` the received lists) and the public `GET /pages/{id}/events` (`page` refetches the tips, spin and effects answers and the viewer's allowances).
- **Theming** is Tailwind v4 `@theme` tokens in `src/index.css` (e.g. `bg-card`, `text-leaf`, `font-display`). Dark is the default; light is the same token names overridden under `prefers-color-scheme: light`. Use the tokens, not raw colors.
- **Localization** is `src/i18n.ts`: wrap every user-visible English string in `t("...")` (placeholders like `{name}` filled from the second argument) or `tRich("...", { link: <a>...</a> })` for sentences with elements in them. The English string is the key, and `scripts/translate.py` (`just machine-translate`, like Moblin's) finds them with a regex, so the first argument must be a double-quoted literal (or literals joined with `+`), never a variable. It also picks up the `<title>` of every HTML entry, which `i18n.ts` translates. Translations live in `src/locales/<code>.json`, one per language, and only the chosen one is loaded, with top-level await before any module using `t()` runs, so `t()` works at module level in `src/data/`. The language comes from the footer's picker (saved in `localStorage`, reloads the page) or the browser. Strings without a translation show in English; run `just machine-translate` after adding or changing strings. The Terms page, the admin page and backend error messages stay English.
- Icons are inline stroke SVGs in `components/Icon.tsx` keyed by `IconName`; platform logos on a colored disc are `BrandIcon`.

## Backend architecture

One binary, `backend/src/main.rs`, wired together from the modules below. It stops on SIGTERM or Ctrl-C by finishing the requests in flight first (axum's graceful shutdown), so a deploy never cuts a payment capture off between taking the money and saving the delivery; the device event streams, which never finish by themselves, end when the shutdown starts (`Api::stopping`) so they do not hold it up.

- `api.rs` — the axum router, `Api`, `Failure` and the session checks (`signed_in`, `admin`, `assistant`); the handlers are in `api/` by feature (`streamers`, `sign_in`, `account`, `settings`, `assistants`, `devices` for watching and controlling a device, `providers` for connecting PayPal and Stripe, `public` for the public page answers, `tips`, `spins`, `effects`, `subscriber`, `orders` for creating, capturing and settling payments, `recent`, `banner`, `test_sends`, `monitor` for the monitor layouts, `admin`), each with its tests. `GET /account/pages/{id}/monitor` answers the caller's monitor `layout` for that page (the page's own account or one of its assistants, `assistant()`), else the one they saved most recently for any page, else null; `POST /account/pages/{id}/monitor` saves `layout`, an object at most 16 KB (413 past it, 422 `invalid-layout` otherwise) the backend stores as it is (`Accounts::monitor_layout` and `set_monitor_layout`, the `monitor_layouts` table keyed by the account and the page). The WebSocket, Twitch and Kick callbacks and PayPal webhook paths are registered outside this repo (in Moblin, Twitch's, Kick's and PayPal's consoles) and must not be renamed, and `GET /pages/addresses` is a contract with the Moblin website's backend. Every account has a page, created with its Moblin Cloud key in the sign in callback of the platform that created it, and managed by the signed in account, whichever linked platform it signed in with. An account has one Moblin Cloud key (a random lowercase version 4 UUID from `Streamers::new_key`; `key` in the signed in account, replaced with `POST /account/key`, which disconnects every device), only used by Moblin's WebSocket and only leaving the backend in the signed in account, which the streamer pastes into the global Moblin Cloud settings of up to 5 devices running Moblin; Moblin connects to `/remote-control/streamer/{key}` under its `MOBLIN_CLOUD_API_URL`, separately from its own remote control. The page's public id is 12 random bytes in base64url (`Streamers::new_page_id`), unrelated to the key, and stays when the key is replaced. A device is told apart by the `streamerId` of its `identify` message (Moblin's per install id): one without it is refused, as is a sixth device of a page, both answered `identified` with an `error` result (Moblin shows "Failed to identify" and keeps retrying) before the socket is closed (`remote_control::refuse`), while a device connecting again replaces its old session in its place, keeping its wheel until Moblin pushes it again. A session whose connection ended without a close frame of code 1000, normal closure, (a transport error, a failed send, 60 s without a message or any other close; Moblin never sends a close frame, as NWWebSocket's `disconnect()` only cancels the connection, so this is every disconnect of today's Moblin, turning Moblin Cloud off included) is kept `reconnecting` for a minute (`Streamers::new`'s linger, zero in the tests but `sessions_wait_for_the_device_to_reconnect`) so a device with flaky internet comes back to the same session: it keeps its place, its wheel (so the page still takes spins and the settings' `connected` stays true) and counts towards the 5 devices, but gets no requests (`RequestError::Offline`, so deliveries wait for it to reconnect), is not counted in `connected_count` and is shown as `reconnecting` in the dashboard's device list; a 1000 close ends the session at once (the system tests' relay in `tests/utils/moblin.py` sends it when the tester changes Moblin's settings, and 1001 otherwise, so its `disconnect()` acts like a dropped connection). Remote control sessions are per page and device, in the order they connected: wheel spins use the page's wheel device, the first with a wheel picked there (else the first one), and tips and effects go to every known device of the page (`Deliveries::tip_devices`), each as it connects; the settings' `connected` is whether any device is. The signed in account's `devices` lists the page's known devices, the connected ones first in the order they connected and then the others, seen most recently first, each with its `name` (`Moblin <number>` with the smallest number no other device of the page is named with, given when the page first sees it, or the name the streamer gave it with `POST /account/devices/{device}/name`, 1 to 30 characters; `Accounts::seen_device` and `rename_device` in the `devices` table, keyed by the account and the `streamerId`, its `last_seen` updated when it connects and when it disconnects (`Accounts::left_device`), forgotten with its name after 30 days unseen or when the streamer removes it with `POST /account/devices/{device}/remove` (`Accounts::remove_device`, 409 `Turn off Moblin Cloud on the device first.` while it is connected, since it would come back at once; tips then stop waiting for it), and at most 20 kept per account, a new one replacing the one seen longest ago), whether it is `connected` or `reconnecting`, whether it is the `wheel` device and, when not connected, when it was last seen (`lastSeen`, unix seconds), which the dashboard's Moblin section shows. Spins without a payment are only those of Twitch and Kick subscribers (`subscribers.rs`) and the streamer's and assistants' own tests. Tips need no connected streamer; a completed tip capture queues the tip (`deliveries.rs`) for Moblin. Wheel spins need Moblin's wheel (`wheel`, so a connected streamer that sent one) both to create an order and to capture it; a completed spin capture queues the spins the same way. Order requests take an optional `provider` (`paypal`, the default, or `stripe`), the public tip and spin answers carry the PayPal fields and `stripe` (publishable key and connected account) for whichever the streamer connected, and a Stripe order also answers its `clientSecret`. Tip and spin orders share `capture_order`, which refuses an order of another kind (`Item::kind`), and cancels a Stripe payment it refuses because the wheel is gone, so the hold on the viewer's card is released. A capture moves the order through the stages in `payments.rs`: `created` to `capturing` before the provider is asked (a database that cannot be written refuses the capture with 503 `not-saved` before any money moves; two captures at once are harmless, since the provider answers the second one already captured and `record_capture` saves a capture once), then `captured` together with its delivery in one transaction (`record_capture`); the stages only move forward, so an order the provider refused (402 `declined`, a 4xx so the page does not retry it) or the viewer had not approved (402 `not-approved`) stays `capturing` like one the provider reviews, and `capturing` means the provider has been asked at least once, so the money may have been taken and only the provider can tell. When the provider's answer is lost (a transport error, a 5xx or an unreadable body, `CaptureError::Unknown`), the capture handler looks the order up at the provider at once (`settle_one`) and only answers 502 `unknown` ("did not answer. If the money was taken, the tip will still be shown.") when the lookup fails too; a retried capture of a capturing order looks it up again and, when the provider has not captured it, runs the same checks as a first capture (the wheel for spins) and captures it again (a second capture can't take the money twice), and a captured one answers 202 again; a capturing order the provider has not captured stays capturing, since a lost capture may still complete after the lookup, until `settle_orders` finds it still not captured 30 minutes after it was created and removes it (cancelling a Stripe payment), so the page retries a capture on network errors and 5xx answers (three times) without ever showing an error for a payment that went through. An order has 30 minutes from its creation to be paid (`Saved::late`, `DEADLINE` in `payments.rs`), since a tip that late is no use on stream: a capture of a created order past it is refused with 410 `too-late` before the provider is asked, and money a lookup finds taken past it (a lost capture answer or a pending review completing late) is refunded instead of delivered (`refund_late`: `PayPal::refund`, the order's capture refunded with `PayPal-Request-Id` `refund-<capture id>`, which needs the `REFUND` feature the referral asks for, and `Stripe::refund`, `POST /v1/refunds` with `Idempotency-Key` `refund-<payment id>`), the order removed and counted as `<kind>Refunds` and `<provider>Refunds`, with 410 `refunded` to a viewer who retries; a refund the provider refuses (a streamer who connected PayPal before the `REFUND` feature was asked for) delivers the payment late instead (`<provider>RefundsFailed:provider`), and one whose answer was lost is retried every minute (`:unknown`). `settle_orders` is a background task that, every minute, looks up every capturing order older than a minute (`PayPal::status`, `Stripe::status`) and queues the delivery of those the provider captured, so a pending review that completes days later, a capture whose answer was lost or a crash between the provider's answer and the database still deliver. The `/account/test/*` routes let the signed in streamer send themselves a free tip or wheel spin from the dashboard's Tips and Wheel of luck sections, to check that Moblin gets them: they skip payment and need no PayPal or Stripe, but run the same Moblin checks as paid ones (the wheel for spins, nothing for tips, which wait in the queue for Moblin like paid tips), so spins are refused with 409 `Connect Moblin first.` without a connected device; all are refused with 429 past 10 tests a minute per page (`Api::tests`, in memory), and queue a delivery under the account's name with the first suggested tip amount (5.00 without tips) or the first spin option's spins (1 without a wheel option). `GET /account/recent?kind=<tip|spin>` pages through the signed in streamer's captured orders of that kind, newest first (`Orders::recent`, by the `kind` column and the `orders_recent` index; captured orders are kept 30 days, so that is the whole history), `limit` of them (20 by default, at most 50) `before` the order id given, answering `items` and whether there are `more`; test deliveries are not listed. A paid item has its `provider` (`paypal` or `stripe`), only in the streamer's own list, never in an assistant's (`GET /account/pages/{id}/recent`). Each item has its `status`: `delivered` when its delivery is finished (or no delivery row is left), `waiting` while Moblin has not got it, and its `devices` with whether each `received` it (a finished delivery lists only the devices that got it, an unfinished one also the ones it still waits for: every connected and known device for a tip and the wheel device for a spin), which the dashboard shows in place of a status, except `waiting` with no device listed ("Waiting for Moblin"). The dashboard shows each kind under its section's test card (`Latest` and `createRecent` in `components/Latest.tsx`): the first 5 when the dashboard opens, then 20 more per Show more, refreshed (the shown ones, at most 50; older loaded ones are kept) on the page events' `recent`, each item with a Send again button (`POST /account/recent/{order}/resend`, or `/account/pages/{id}/recent/{order}/resend` for an assistant) that queues the captured order's delivery again (`Deliveries::resend`: the delivery row is reset, or inserted when it was pruned, with `resends` bumped, so Moblin gets it under a new `requestId` of `<order id>-<resends>` and its dedup does not swallow it; it then shows as `waiting` until Moblin gets it). Viewer-facing errors are full sentences the page shows as they are. `GET /admin/stats` is for the site operator: the Twitch user ids, or `kick:<Kick user id>`, in `--admins` (env `ADMINS`, comma separated) are admins (an account is an admin when any of its identities is listed, `Identity::admin_key`), `GET /account` answers `admin` for them and everyone else gets 403; it answers counts of accounts (total, PayPal and Stripe connected, and premium: signed in admins and `--premium-accounts`), connected devices (`connected_count`, every session of every page) and the remote control `messages` sent to and received from Moblin's WebSocket connections (`traffic.rs`, `Streamers::traffic`: the `messages` and `bytes` per `kind`, the request or event name, `hello`, `identified`, `pong`, `ping`, `identify` or `response:<result>`, with an unreadable message as `invalid` and kinds past the first 100 as `other`; in memory only like the requests, shown as two tables in the admin page's Moblin section), unfinished orders and pending deliveries that no device has received yet (a tip some of the page's devices got is not pending; plain column counts, no JSON is read), the SQLite database size (`database`: the total `bytes` and the `files` on disk, the main, `-wal` and `-shm` ones that exist, each with its `name` and `bytes`, none in memory; the admin page's Server section lists them with the total), the `server`: its `version` (the release tag, passed to the Docker build as `VERSION` by the deploy workflow and compiled in as `MOBLIN_CLOUD_VERSION`, `dev` otherwise), when it `started` and the server's `now` (unix seconds, for the uptime), its resident `memory` (from `/proc/self/status`, null off Linux), which `integrations` are configured (Twitch, Kick, App Attest, PayPal, Stripe) and its `requests` (`requests.rs`: the `total` HTTP requests answered since it started, the count per `statuses` code and the `endpoints`, each matched route pattern like `/pages/{id}/tips` (axum's `MatchedPath`, `*` for requests matching no route) with its own `total` and `statuses`, most requested first; from a `middleware::from_fn_with_state` layer outside the CORS layer that counts each response in a map of the pattern's status counts behind a mutex, in memory only, so a restart starts over; the admin page's Server section shows them as tiles, a status table and an endpoint table with 4xx and 5xx columns, with 5xx counted as Server errors), plus the event `counters` (`counters.rs`); unfinished orders are those not yet captured. The change streams (`api/events.rs`) are fed by `Changes` in `changes.rs` (`Streamers::changes`), a broadcast channel per page that is only kept while someone listens: `Change::Page` for anything the public page shows (settings, banner, PayPal and Stripe connected or not, linked platforms, a device connecting, reconnecting, leaving or pushing its wheel), `Change::Account` for what only the dashboard shows (device names and removal, assistants, which also tells the assistant's own page, an onboarding started) and `Change::Recent` for a captured or resent order and a delivery a device got. `GET /account/pages/{id}/events` sends `account` for both of the first two and `recent` for the last (both when it lagged) and checks the assistant again every minute like the device stream; `GET /pages/{id}/events` (404 for an unknown page) sends `page`; `GET /admin/stats/events` sends `stats` at once and every 2 s while the account is still an admin. All of them end when the shutdown starts. CORS allows only the origin of `--frontend-url` (env `FRONTEND_URL`). The backend does not start without `--backend-url` (env `BACKEND_URL`, its own address, from which it makes the sign in callbacks) and `--frontend-url`, which have no defaults so a copy never points at cloud.moblin.app by mistake.

- `app_attest.rs` — verifies Apple App Attest attestations and assertions so only the Moblin app can connect to Moblin Cloud (a copy of the Moblin website's, which checks its live post with it): `Attestation` is the base64 fields a client sends (`keyId`, `attestation`, `attestationChallenge` and the `assertion`, all optional so a missing one is a clear error; a malformed `appAttest` in Moblin's identify is read as an empty one, so it fails as `invalid` instead of making the whole message fail to parse), and `verify` checks them against some client data, the hello challenge of the WebSocket. Stateless by design: the app resends its attestation every time and the server re-verifies the chain each time, deliberately ignoring certificate validity dates. Tests use public sample vectors in `src/testdata/`.
- `remote_control.rs` — the assistant side of Moblin's remote control protocol, for tips and wheel spins on the page. Moblin Cloud connects with the key in the URL and an empty password, which the backend does not check. Moblin proves it is the Moblin app with App Attest in `identify`: an optional `appAttest` with the same `keyId`, `attestation` and `attestationChallenge` its live post to the Moblin website sends (the key attested once per device for the live post is reused) plus an `assertion` whose client data is the raw bytes of the hello `challenge`, the fresh random 64 bytes the backend sent on this very connection, so no separate challenge round trip or `Challenges` entry is needed (`Identity` from `identify`, checked by `AppAttest::verify` in `handle_remote_control_streamer`). Unless `--allow-unattested`, every connection is verified (logged when it fails: no `appAttest`, an older Moblin, or an invalid one), and with `--require-attested-moblin` (env `REQUIRE_ATTESTED_MOBLIN`) the failed ones are refused like one without a device id. Moblin Cloud is off in Moblin on Mac, where App Attest is not supported. Serde types mirror Swift's synthesized `Codable` (`{"ping":{}}`, optional fields omitted), and must match `Moblin/RemoteControl/RemoteControl.swift` in the Moblin repo. Moblin pushes its wheel (the wheel of luck widget picked in Moblin's Moblin Cloud settings) as a `wheelOfLuck` event on connect and on every change; it is kept with the session and served by `GET /pages/{id}/spin` as `wheel` for the page to draw, next to `connected`, so the page can tell a streamer who is offline from one who picked no wheel (whose spin orders are refused with 409). Moblin also pushes the icon shown in the top right of its UI (the one picked in its Store settings, `iconImage`) as an `icon` event (`{"icon":{"id":"AppIconKing"}}`) on connect and on every change; `serve` hands a known one to its caller, which saves it as the page's (`Pages::set_icon`, the `page_icons` table, the last one any device sent), and unknown ids are ignored. The requests sent are `tip`, shaped like Moblin's `music` request: viewer `name`, `message`, `requestId` and a `kind` (`TipKind`, Moblin's `RemoteControlTipKind`) of `message` (amount as a string like `7.00` and currency), `effect` (for a sound effect its Moblin name as `sound`, like `Bad chili fart`) or `wheelOfLuck` (number of spins as `count`), answered `ok` without data and deduplicated by Moblin on `requestId`; and the monitoring and control of a device for the device page (`Streamers::watch`, `control`). Each watched device (page and device, whether or not it has a session) has a `Monitor` in `Sessions::monitors`, created by the first watcher's `watch` and removed with the last: the number of `watchers` (open event streams), the merged `status` (Moblin's `RemoteControlStatusGeneral`, `TopLeft` and `TopRight` as `general`, `topLeft` and `topRight`, each replaced whole when a `status` event carries it), the merged `state` (Moblin's `RemoteControlAssistantStreamerState`, the keys of each `state` event written over the old), the last `settings` (Moblin's `RemoteControlSettings`, from the `data` of any `getSettings` response, whoever asked) and a broadcast channel of `Update`s that every watcher's stream reads; it outlives the device's sessions, so watchers keep it when the device reconnects. The first watcher's `watch` sends `startStatus` (interval 1, filter `topRight` true) and a `getStatus`, every watcher's a `getSettings`, all without waiting for the answer (`Session::send`; the settings and status answers are picked up in `handle`, a `getStatus` answer merged like a `status` event but without a sample), and a task per watched device (`poll_status`, spawned with the monitor) sends `getStatus` every 5 s until the last watcher is gone, since the periodic event only carries the top right part, a device connecting while it has watchers is sent them again (`resume_watching`) and the last watcher's guard sends `stopStatus` when dropped, so Moblin pushes status only while a page is open, and a device that lost its connection or connected tells the watchers `connected` false or true. Controls (`Control`, serialized flat as Moblin's requests through the untagged `Request::Control`) wait 5 s for the `ok` like tips. Moblin's Moblin Cloud side is `MoblinCloud` in Moblin's `ModelMoblinCloud.swift`: on `startStatus` it sends the full state and then, from Moblin's 1 s timer, a `status` event built with the request's filter like its regular remote control streamer does (so only `topRight`, the general and top left parts coming from the backend's `getStatus` every 5 s), until `stopStatus` or the connection drops; it forwards `state` changes while asked, answers `getSettings` with Moblin's settings and forwards the controls above to the `Model` methods shared with its remote control streamer's delegate (`remoteControlSetLive`, `remoteControlGetSettings` and so on in `ModelRemoteControl.swift`, or the plain ones like `selectScene`; neither delegate calls the other's `remoteControlStreamer*` methods). `topRight` carries, besides Moblin's display strings, `bitrateInfo` (`bitsPerSecond` and `totalBytes`, while live) and `bondingInfo` (per SRTLA or RIST connection its `name`, `bytesPerSecond` and `rtt` in milliseconds, while bonding), added to Moblin's `RemoteControlStatusTopRight` for the graphs. The preview: `GET /account/pages/{id}/devices/{device}/preview` (`api/devices.rs`, the same checks as the event stream but with `previewer` in place of `watcher`, so an assistant without `preview` gets 403 `no-preview` `The streamer has not let you see the stream preview.`, also on the minute's recheck, which ends an open stream once it is turned off) is a server-sent event stream of `frame` events (`image`, the base64 image of Moblin's `preview` message, at most 2 MB); its first watcher's `Streamers::watch_preview` sends `startPreview`, a device connecting while it has watchers is sent it again, the last watcher's guard sends `stopPreview`, and the last frame is kept for new watchers (`PreviewMonitor` in `Sessions::previews`, apart from the status monitors). Moblin Cloud forwards these controls to the `Model` methods its remote control streamer uses too (`remoteControlSetFilter`, `remoteControlSetPreviewStream`, `remoteControlSendMessage`, `setGimbalTracking`, `startMacro`, `stopMacro`), and between `startPreview` and `stopPreview` sends a `preview` frame of Moblin's low fps image, at least one a second (`MoblinCloud.requestingPreview`, counted in `setLowFpsImage`), only in Moblins from after these were added; older ones ignore them. Older Moblins answer empty settings, push nothing and ignore the controls.
- `effects.rs` — effects, the third paid kind next to tips and wheel spins (`Item::Effect`, `kind` `effect`, counted as `effectOrders`, `effectPayments`, `effectTests`, `effectDeliveries` and so on): the viewer pays the page's one effect price (the page setting `effects`, `pages::Effects`) to have Moblin play the effect they picked, with an optional name and message. Only sounds for now (`kind` `sound`), the fart sounds of Moblin's `Alerts.bundle`, copied into `src/effects/` and compiled in, each with an id (`fart`, `fart-2`, `bad-chili-fart`, `perfect-fart`), its Moblin name and its content type. `GET /pages/{id}/effects` answers the paid `effects` (the price and the payment fields like the tips answer, null when off), `subEffects` and the `options` (each effect's `id` and `kind`), `GET /effects/{id}` serves the media so the page plays a sound when the viewer taps it, `POST /pages/{id}/effects/orders` takes `effect` (400 `no-such-effect` for an unknown one) and the shown `price` (400 `invalid-option` when it changed), and the delivery goes to every device like a tip, as a `tip` request of kind `effect`. Subscribers get effects without a payment like wheel spins (`subscribers.rs`, the page setting `subEffects`). `GET /account/recent?kind=effect` answers the `effect` of each item, and the dashboard's test effect sends the picked one (`effect` in `POST /account/test/effect`, the first one without it).
- `icons.rs` — the icons Moblin shows in the top right of its UI (its `AppIcon*NoBackground` images, the plain one and the Store's, copied into `src/icons/` downscaled to 256 pixels high and compiled in), each with an id (`plain`, `king`, `san-diego` and so on) and its Moblin id (`AppIcon`, `AppIconKing`, ...). `GET /icons/{id}` serves the PNG; the page's `icon` is shown on the tip page below the channel link, or right of the streamer's avatar, cut out of the banner like the avatar, when the page has a banner (`MoblinIcon` in `pages/Page.tsx`). A new Store icon in Moblin needs a row here, or the backend ignores it.
- `database.rs` — the SQLite database (`rusqlite`, SQLite bundled) at `--database`, in memory without it, shared by `Accounts`, `Pages`, `Orders`, `Deliveries` and `Counters` behind one mutex. Tables are created with `CREATE TABLE IF NOT EXISTS` on start and there are no migrations, so a schema change needs the existing database changed by hand.
- `counters.rs` — event counters for the admin page, one row per name and UTC day in the `counters` table, read back as today, last 7 days and all time. Measurement points come in pairs, `<name>` for successes and `<name>Failed:<reason>` for failures, where the reason is the `reason` slug every `Failure` in the API carries (`counted` does the bumping), which the admin page lists as one plain row per reason under the success row, always showing the reasons each code path can produce (`failures` per event in `Admin.tsx`, labels in `reasonLabels`) plus any unexpected one that occurred: created orders and captured payments (`tipOrders`, `tipPayments` and so on per `Item::kind`, any refusal or provider error counting as failed), the same per provider (`paypalOrders`, `stripeOrders`, `paypalPayments`, `stripePayments` by `Payee::slug`: orders from the moment the provider is asked to create one in `start_order`, captures from the moment it is asked to capture in `capture_at_provider`, so the page's own refusals before that only count under the kind; a captured payment counts for its kind and its provider in the same transaction), spins of subscribers (`subSpins`), the dashboard's free test sends (`tipTests`, `spinTests`; their deliveries and expiries are counted as `tipTestDeliveries`, `tipTestExpiries` and so on, shown in their own Tests table and left out of the Problems), and in `deliveries.rs` a delivery that reached every device (`tipDeliveries`, `spinDeliveries`) or that Moblin refused (`...DeliveriesFailed`, once per delivery and reason). The free `counters::bump` takes a connection, for callers already holding the database lock.
- `pages.rs` — per streamer page settings (`Pages`), keyed by the public id: the one currency of all its payments (USD by default, set in the dashboard's Payments section; only changed while tips, the wheel and effects are all off, refused with 409 otherwise, so their amounts never silently switch currency; turning one on in the same save as the currency is fine, and the dashboard disables the picker while one is on), optional tips (one to five suggested amounts in hundredths), optional effects (one price), an optional spin wheel (one to five options of a number of spins and its price) and the subscriber tiers, each a `Feature` with an `enabled` flag next to its values, so turning one off keeps its values for when it is turned on again (`enabled` defaults to true, so settings saved before the flag are on; the checks and the public answers only see features that are on, through `Settings::tips()` and the like, and the public answers show one that is off as null) and the look of the page (message up to 300 characters, accent color from a fixed list whose CSS lives in `index.css` as `[data-accent]` overrides of the moss/leaf tokens, or for premium accounts any `#rrggbb` color, drawn as `[data-accent="custom"]` with the color in `--accent` (`accentAttributes`; a streamer taken off `--premium-accounts` keeps theirs but can't pick a new one), and, for premium accounts, a font from a fixed list (refused with 403 for others, who likewise keep one picked while premium), `[data-font]` overrides of `--font-display`/`--font-body` whose Google Fonts `loadFonts` adds only when used). `GET /pages/{id}` returns the look with the name, avatar and banner image version (`images.rs`). Saved as JSON in the `pages` table on every change.
- `auth.rs` — streamer sign in with Twitch (OAuth authorization code, `OAuthApp`) or Kick (OAuth authorization code with PKCE S256, `KickApp`: authorize at `https://id.kick.com/oauth/authorize`, token at `https://id.kick.com/oauth/token` with the `code_verifier` kept with the state, scopes `user:read channel:read`, the user from `GET https://api.kick.com/public/v1/users` and the login from the channel `slug` of `GET https://api.kick.com/public/v1/channels`, both answered for the token's own user; the Kick user id is a number, read as text; `--kick-client-id` and `--kick-client-secret`, env `KICK_CLIENT_ID` and `KICK_CLIENT_SECRET`, without which `GET /auth/kick/login` answers 503), each callback giving an `Identity` (platform, user id, lowercase login, name, avatar), with one-time states (`SignInState`: the viewer's page, whether it is a link and the PKCE verifier) that last 10 minutes and must match the `moblin_sign_in_state` cookie set by `GET /auth/<platform>/login`, so a callback URL only works in the browser that started the sign in. `signed_in_redirect` in `api/sign_in.rs` handles both platforms: a normal sign in finds the account of the identity (`Accounts::signed_in`) or creates one with a random id and a new page, and redirects to `/dashboard/#session=<token>`; `?link=1` on the login route makes a link flow, whose callback does not touch any account but redirects to `/account/#link=<link token>` (`#linkFailed` when it failed), a signed token prefixed `link:` holding the identity for 10 minutes (`Auth::link_token`, `link_of`), which the Account page posts to `POST /account/link` with its session, so the identity is linked to the account whose browser finished the flow and a callback link handed to someone else links their own identity to their own account; `POST /account/unlink/{platform}` removes a linked identity, 409 for the last one. Sessions are `<account id>:<generation>:<issued>` signed with HMAC-SHA256 under `--session-secret` (random without it), 30 days, sent as a bearer token (`signed_in` in `api.rs` also accepts a session whose account id is a Twitch user id, from before the ids were renamed, by looking the account up through its Twitch identity, so renaming signed nobody out); viewer (`viewer:`) and link (`link:`) tokens are signed the same way and none is accepted as another. A session is only accepted while its generation matches the account's `sessions` counter, which signing out increments; starting to connect PayPal (`POST /account/paypal/connect`) needs a session issued in the last 10 minutes. The Twitch and Kick URLs are fields of `OAuthApp` and `KickApp` so tests can point them at a local server.
- `accounts.rs` — one account per streamer, keyed by a random id of 32 hex characters (`Streamers::new_account_id`), with its linked identities in the `identities` table (`Identity`: `platform`, `twitch` or `kick`, `user_id`, `account`, `login`, `name`, `avatar`; primary key platform and user id, so a platform account belongs to one Moblin Cloud account), each giving the page an address, `/twitch/<login>` or `/kick/<login>` (`page_of_login` per platform; a login is unique per platform: it is taken from other identities on sign in, after renames, which leaves theirs empty). `signed_in` finds the identity's account or creates one (the account row with its key, its page's settings row and the identity in one transaction) and answers the id with the account; `link` adds an identity to an account and refuses one that belongs to another account (`IdentityTaken`, 409 "This Kick account already has its own page. Delete it first."; nothing is ever merged); `unlink` removes one and refuses the last (`LastIdentity`, 409). The account's name and avatar (`Account::name`, `avatar`, for the dashboard header, test sends and the Stripe account name) are those of its Twitch identity when it has one, else its Kick one; the pages show the identity of their address. Its page: a public id fixed at sign in, its Moblin Cloud key (`moblin_key`, uniquely indexed so the WebSocket route's `page_of_key` is an indexed lookup; `POST /account/key` replaces it and the WebSocket route only accepts the current key), and its PayPal: the merchant ID every paid feature of the page pays (`merchant_of`) and the tracking ID of an unfinished onboarding, and its Stripe connected account with whether it takes payments yet (`stripe_of`, only ready accounts). The merchant ID only ever comes from PayPal's seller onboarding (Partner Referrals): `POST /account/paypal/connect` creates a referral and answers PayPal's sign up link, and `POST /account/paypal/check` looks the tracking ID up with PayPal and connects the merchant ID once it can receive payments, has a confirmed email and granted our app third-party permissions; the return URL's parameters are never trusted. `POST /paypal/webhooks` (verified with PayPal's verify webhook signature API under `--paypal-webhook-id`) connects pending onboardings on `MERCHANT.ONBOARDING.COMPLETED` through the same `finish_onboarding` checks and disconnects merchants on `MERCHANT.PARTNER-CONSENT.REVOKED`; `POST /account/paypal/disconnect` forgets the merchant ID and any unfinished onboarding. Paid features can only be turned on or changed while PayPal or Stripe is connected. Saved in the `accounts` table. `POST /account/delete` (`Accounts::delete`, the Account page, with a confirm) removes the signed in account and everything it owns in one transaction: the account row, its identities, its devices, its monitor layouts and those others saved for its page, both directions of each identity's assistant rows, its page's settings, banner image, Moblin icon, orders, deliveries and subscriber allowances; the handler then disconnects its Moblin devices, and signing in again starts a new account with a new page id. PayPal and Stripe accounts are never touched.
- `paypal.rs` — PayPal partner client: seller onboarding (`referral`, `seller`, which need the partner's merchant ID `--paypal-partner-id`; `--paypal-attribution-id` is the BN code sent with every request), webhook verification and Orders v2, created and captured for the streamer with an unsigned `PayPal-Auth-Assertion` JWT naming their merchant ID, for tips and wheel spins (an order's `Item` is a tip with its message or a spin purchase with its number of spins and message): orders name the streamer's PayPal merchant ID as payee so money goes straight to them (never the email: PayPal no longer accepts emails as the SDK's `merchant-id`, and it would be public), with `payment_source.paypal.experience_context` asking for no shipping and `IMMEDIATE_PAYMENT_REQUIRED`, so funding that settles later (eCheck) is not offered and fewer captures end pending. A completed capture whose amount matches queues the delivery; a pending one (PayPal still reviewing it) is settled later by `settle_orders`, which asks `status` (GET the order).
- `stripe.rs` — Stripe Connect platform client, the alternative to PayPal. Streamers get a connected account (Accounts v2 API, full Stripe Dashboard, Stripe collects fees and losses) created on the first `POST /account/stripe/connect` in the country the streamer picks (`stripe::COUNTRIES`, the countries Stripe takes sign ups from, also listed in the frontend; Stripe can't change it later), which answers a Stripe-hosted onboarding link back to `/dashboard/?stripe`; `POST /account/stripe/check` marks it ready once its `card_payments` capability is active. Payments are direct charges on the connected account (`Stripe-Account` header): a PaymentIntent (v1 API) with `capture_method=manual`, no redirect payment methods and no application fee, confirmed in the browser with the client secret and captured by the backend, like a PayPal order. On the page, "Pay with Stripe" creates the order first (so the viewer sees the final price) and then shows Stripe's Payment Element; changing the form closes it. `status` (GET the PaymentIntent) settles payments whose capture answer was lost. There are no Stripe webhooks; a revoked account only fails new payments until the streamer checks again. `--stripe-secret-key` and `--stripe-publishable-key`; a test mode key takes test payments.
- `payments.rs` — what is provider neutral about payments: the order (`Item`, `Order` with its `Payee`, a PayPal merchant ID, a Stripe account, or `Twitch` with the tier or `Kick` for a subscriber's spin, saved already captured and never reaching a provider, and its description), `CaptureError` (`NotApproved`, `Pending`, `Refused` when the provider definitely said no, `Unknown` when its answer was lost; an order the provider has already captured is `Ok`), `PaymentStatus` (what a lookup at the provider says: captured, pending, not captured or gone, or refunded after a late payment), `RefundError` (`Refused`, `Unknown`) and `Orders`, every order in the `orders` table with its `Stage` (`created`, `capturing`, `captured`) and the order as JSON, so a restart loses no payment: `start_order` inserts after creating the provider's order (refusing the order with 503 `not-saved` if that fails), `transition` is a compare-and-set between stages, `captured` runs the stage change and the delivery insert in one transaction, `get` reads an order with its stage and whether it is past the deadline (`Saved`), `unsettled` lists the capturing orders older than a given age for `settle_orders`, `expire` drops created orders after 30 minutes (`settle_orders` then cancels their Stripe payments, so a viewer whose capture never reached the backend gets the hold on their card released), `make_room` refuses new ones past 10000 unfinished, `captured` does nothing for an order already captured and otherwise counts `<kind>Payments` in the same transaction as the delivery, so a payment is counted once however it was found, and `prune` gives unsettled orders up and forgets captured ones after 30 days.
- `deliveries.rs` — at least once delivery to Moblin of tips and wheel spins, saved in the `deliveries` table. Deliveries are kept per page and their devices picked when delivering: spins go to the wheel device and tips to every device the page knows (`tip_devices`: the connected ones and those in the `devices` table, so one briefly disconnected when the tip was ordered still gets it when it connects again), tracked in `delivered` (by `streamerId`) so each device gets a tip once; a tip is finished once a device got it and every known device has it, so a tip waiting for a device that never comes back stays unfinished until it is given up after 7 days or the device is forgotten, and a device connecting while a tip waits gets it too. A delivery every device got is marked `finished` and kept 30 days, so the dashboard can tell which devices got a tip. Test deliveries (`add_test`) are marked with their kind in `test`, and only the 5 newest per page and kind are kept. A background task delivers them whenever a device connects, after a request and every 10 s, each connected device concurrently, by sending `tip` with the request id (random, or the PayPal order id) as `requestId` until Moblin answers `ok`; Moblin's own dedup on `requestId` makes the retries safe. A Moblin `error` is temporary and retried; `failure` records the latest reason so each failure is counted once per delivery and reason. A delivery waits in the table until a device gets it and is only given up after 7 days (the one way a paid request is allowed to fail), counted as `tipExpiries` or `spinExpiries` when no device got it.

Everything optional degrades rather than fails: without Twitch credentials, Twitch sign in answers 503; without Kick credentials, Kick sign in answers 503. `--allow-unattested` disables App Attest for Moblin Cloud (so any client, the fake Moblin included, connects, whatever `--require-attested-moblin` says), `--twitch-sign-in-url <base>` points the sign in's OAuth and Helix endpoints (`OAuthApp::at`) at another server and `--kick-sign-in-url <base>` Kick's (`KickApp::at`, including the website API's `channel_users_url` the subscriber check uses), with no client ID or secret needed, both for local development and the system tests only. There is no fake logic in the backend: the fake Twitch is `tests/utils/fake_twitch.py` (stdlib only), an HTTP server whose authorize page lets the browser pick any made-up login (or takes it as `login` in the query, which the system tests do), whose user id is a 9 digit number hashed from the login (`user_id_of`, like Twitch's numeric ids), with a login ending in 1 to 3 subscribed at that tier to everyone and any login but `nobody` resolved by its users endpoint under an app access token (client credentials); the fake Kick is `tests/utils/fake_kick.py`, the same for Kick's OAuth (checking the PKCE challenge, with client credentials for the username lookup), public API (also by `slug`) and the website API's channel user (a login ending in 1 to 3 has a subscriber badge), whose user id is an 8 digit number hashed from the login, so the same login on both fakes is two different users until linked. `just dev-backend` starts them on ports 8081 and 8082 and passes both options, with `--admins` holding the user ids of `admin` on both, making it an admin, and so premium, and `--premium-accounts` those of `premium`, making it a premium account; `normal` is neither. The system tests start both on free ports when `[twitch] sign-in` is `fake` (`Backend.fake_twitch`, `Backend.fake_kick`).

## Conventions

- **Do not write comments or docstrings.**
- **Magic numbers are fine, and often preferred, when used in a single place.** Do not hoist a literal
  into a named constant just because it is a literal — only name it when the same value is used in more
  than one place.
- Rust edition 2024 (let-chains are used). Clippy warnings are errors in CI.
- Moblin's remote control messages (`remote_control.rs`) are a contract with the Moblin iOS app; changing them requires an app change too.

  messages.
