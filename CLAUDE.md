# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The landing page for Moblin (moblin.app) and its companion apps. Two independent
projects live here:

- `frontend/` — a static site (SolidJS + TypeScript + Tailwind v4 + Vite), deployed to GitHub Pages.
- `backend/` — a small Rust (axum) service deployed at `https://api.moblin.app` as a Docker image. It serves the "Streamers" list and the "Erik is live on Twitch" status.

`README.md` only covers getting started; the deploy flow, App Attest and the Twitch and PayPal setup are described below and in the code.

## Commands

All checks are driven by the `justfile` at the repo root (CI runs exactly these):

```
just style          # oxfmt (frontend) + cargo fmt (backend)
just style-check
just lint           # oxlint --deny-warnings + cargo clippy --all-targets -D warnings
just spell-check    # codespell, configured in .codespellrc
just test           # cargo test (backend only; the frontend has no tests)
```

`just system-test [--device <name>] [pattern]` runs the black box system tests in `tests/` (Python, `systest`, like Moblin's `tests/`): they start the release backend and drive its API like the frontend, with the PayPal sandbox, Stripe's test mode (a new test connected account per run, set up by hand with `--interactive`) and a Moblin whose remote control streamer the tester acts as assistant for and whose Moblin Cloud connectsion it relays to the backend: the fake `tests/utils/fake_moblin.py` by default, a real device with `--device`. `just fake-moblin-run` connects the fake to a running `just backend-run` as the admin user's Moblin (with `--key` taken from the dev database, so sign in as `admin` once first) with a playlist of `--songs` made-up songs (20 by default, 0 in the tests), playing the one in the middle, so the player has something to show. Not run in CI; see `tests/README.md`.

Run a single backend test: `cd backend && cargo test store::tests::list_is_capped` (tests are inline `#[cfg(test)]` modules per file; the API's are under each `api/*.rs`, e.g. `cargo test api::songs::tests`, sharing `start_api_with`, the socket helpers and the fake PayPal, Stripe, Twitch and Kick servers in `api/test_utils.rs` and `api/test_utils/`).

Development needs two terminals:

```
just backend-run    # starts the fake Twitch, then cargo run --allow-unattested with backend/database.sqlite, then seeds fake streamers via scripts/seed_backend.py
just frontend-run   # vite dev server; proxies /api -> localhost:8080
just backend-seed-forever [interval]   # keep posting random streamers to test live updates
```

Frontend build: `cd frontend && npm run build` (runs `tsc --noEmit` first, so type errors fail the build). Backend Docker: `just backend-docker-run`.

## Frontend architecture

- **Multi-page, no router.** Each page is its own HTML entry listed in `vite.config.ts` (`index.html`, `chat-bot/index.html`, `dashboard/index.html`, ...) with its own `src/*.tsx` entry that renders a page component. Sub pages live in a directory so GitHub Pages serves clean URLs like `/chat-bot/`. Add a page by adding all three: the HTML file, the entry, and the `rollupOptions.input` line. `404.html` is what GitHub Pages serves for unknown paths; it renders the page for `/twitch/<login>` and `/kick/<login>` (a signed in streamer's page under the login of that linked platform, showing that platform's name, avatar and channel link; both addresses show the same page and settings), the dashboard for `/dashboard/twitch/<login>` (a moderated streamer's dashboard) and a not found page otherwise. Streamers sign in and manage their page at `/dashboard/`; `/page/?streamer=<id>` shows a page by id and redirects to the dashboard without one. The page header shows a link to the dashboard when the browser holds a streamer session (`readSession`) whose account owns the page (its `settings.id`) or moderates it (`moderating`), to `/dashboard/<platform>/<login>` for a moderator under the platform the page is shown on (`dashboardLink` in `pages/Page.tsx`). Signing in and linking are `PlatformSignIn` in `components/PageParts.tsx` (`signInUrl` and `linkUrl` in `data/account.ts`, the latter `/auth/<platform>/login?link=1`); `/account/` (`src/pages/Account.tsx`, opened from Account in the dashboard's top right menu) holds the Linked accounts section (`LinkedAccounts`), which links and unlinks platforms, Sign out everywhere and Delete account, and redirects to the dashboard when signed out; `createAccountSession` posts the `#link=<token>` the backend's link callback returns to `/account/` to `POST /account/link` with the stored session (so a link only ever lands on the account signed in on that browser), showing the result there (`linkResult`); the Moderators section is hidden while the account has neither Twitch nor Kick linked, and the subscriber songs and spins settings while it has no Twitch linked (`account.twitch`). `/admin/` (`src/pages/Admin.tsx`) shows the operator's statistics from `GET /admin/stats` to a signed in admin, refreshed every 30 s while the tab is visible, and is linked only from the dashboard header of an admin (`admin` in the account answer); it stays English. It opens with a status banner and a Problems table that sum the failure reasons which are our, PayPal's, Stripe's or Moblin's fault (`problems` and `problemReasons`) across songs, tips and spins, with PayPal and Stripe failures as separate rows from the per provider counters, which the Providers section shows in full (orders and payments per provider); viewer mistakes and offline streamers are listed per kind below in muted rows, never counted as problems. `song-requests/index.html` only redirects old `/song-requests/` links to those.
- **Base path is dynamic.** `vite.config.ts` uses `/` when `public/CNAME` exists and `/moblin_website/` otherwise. Anything referencing a file under `public/` must go through `asset()` in `src/asset.ts`; never hardcode a leading slash in a src attribute.
- **Content lives in `src/data/`, not in components.** URLs in `links.ts`, products/features/reviews/chat-bot commands in their own files. Components in `src/components/` are one section each and are composed in order in `App.tsx`.
- **Backend access** goes through `data/backend.ts`: `/api` in dev (proxied), `links.api` in production. `data/streamers.ts` fetches the list once as a module-level SolidJS resource; `twitch.ts` polls `/twitch/live` every five minutes and falls back to "not live" on any error. Every periodic fetch goes through `poll` in `src/poll.ts`, which runs the interval only while the tab is visible and refreshes once when it becomes visible again, so a hidden dashboard or tip page makes no requests.
- **Theming** is Tailwind v4 `@theme` tokens in `src/index.css` (e.g. `bg-card`, `text-leaf`, `font-display`). Dark is the default; light is the same token names overridden under `prefers-color-scheme: light`. Use the tokens, not raw colors.
- **Localization** is `src/i18n.ts`: wrap every user-visible English string in `t("...")` (placeholders like `{name}` filled from the second argument) or `tRich("...", { link: <a>...</a> })` for sentences with elements in them. The English string is the key, and `scripts/translate.py` (`just machine-translate`, like Moblin's) finds them with a regex, so the first argument must be a double-quoted literal (or literals joined with `+`), never a variable. It also picks up the `<title>` of every HTML entry, which `i18n.ts` translates. Translations live in `src/locales/<code>.json`, one per language, and only the chosen one is loaded, with top-level await before any module using `t()` runs, so `t()` works at module level in `src/data/`. The language comes from the footer's picker (saved in `localStorage`, reloads the page) or the browser. Strings without a translation show in English; run `just machine-translate` after adding or changing strings. The Terms page, the admin page, the trading cards, backend error messages and the generated settings reference stay English.
- Icons are inline stroke SVGs in `components/Icon.tsx` keyed by `IconName`; platform logos on a colored disc are `BrandIcon`.

## Backend architecture

One binary, `backend/src/main.rs`, wired together from the modules below. It stops on SIGTERM or Ctrl-C by finishing the requests in flight first (axum's graceful shutdown), so a deploy never cuts a payment capture off between taking the money and saving the delivery.

- `api.rs` — the axum router, `Api`, `Failure` and the session checks (`signed_in`, `admin`, `moderator`); the handlers are in `api/` by feature (`streamers`, `sign_in`, `account`, `settings`, `moderators`, `providers` for connecting PayPal and Stripe, `public` for the public page answers, `songs`, `tips`, `spins`, `subscriber`, `orders` for creating, capturing and settling payments, `recent`, `banner`, `test_sends`, `admin`), each with its tests. Routes: `GET /streamers`, `POST /streamers/live/challenge`, `POST /streamers/live`, `GET /twitch/live`, `GET /remote-control/streamer/{key}` (Moblin's WebSocket), `GET /pages/twitch/{login}` and `GET /pages/kick/{login}` (the page id of a login on that platform), `GET /pages/{id}` (the page's look, with the `twitch` and `kick` identities, null when not linked), `GET /pages/{id}/image` (its banner image), `GET /pages/{id}/songs` (the song price), `GET /pages/{id}/songs/queue`, `GET /pages/{id}/songs/subscriber`, `POST /pages/{id}/songs/subscriber`, `GET /pages/{id}/spin/subscriber`, `POST /pages/{id}/tips/orders/{order_id}/capture`, `GET /pages/{id}/spin`, `POST /pages/{id}/spin/orders`, `POST /pages/{id}/spin/orders/{order_id}/capture`, `GET /auth/twitch/login`, `GET /auth/twitch/callback`, `GET /auth/kick/login`, `GET /auth/kick/callback`, `GET /account`, `POST /account/link`, `POST /account/unlink/{platform}`, `POST /account/key`, `POST /account/devices/{device}/name`, `POST /account/settings`, `POST /account/image`, `POST /account/image/remove`, `POST /account/paypal/connect`, `POST /account/paypal/check`, `POST /account/paypal/disconnect`, `POST /account/stripe/connect`, `POST /account/stripe/check`, `POST /account/stripe/disconnect`, `POST /account/sign-out`, `POST /account/delete`, `GET /account/recent`, `POST /account/recent/{order}/resend`, `POST /account/test/song`, `POST /account/test/tip`, `POST /account/test/spin`, `POST /account/moderators/{platform}`, `POST /account/moderators/{platform}/{moderator}/remove`, `GET /account/pages/{id}`, `POST /account/pages/{id}/settings`, `POST /account/pages/{id}/image`, `POST /account/pages/{id}/image/remove`, `POST /account/pages/{id}/test/tip`, `POST /account/pages/{id}/test/spin`, `POST /account/pages/{id}/music`, `POST /account/pages/{id}/songs`, `GET /account/pages/{id}/recent`, `POST /account/pages/{id}/recent/{order}/resend`, `POST /paypal/webhooks`, `GET /admin/stats`. The WebSocket, live post, Twitch and Kick callbacks and PayPal webhook paths are registered outside this repo (in Moblin, Twitch's, Kick's and PayPal's consoles) and must not be renamed. Every account has a page, created with its Moblin Cloud key in the sign in callback of the platform that created it, and managed by the signed in account, whichever linked platform it signed in with. An account has one Moblin Cloud key (a random lowercase version 4 UUID from `Streamers::new_key`; `key` in the signed in account, replaced with `POST /account/key`, which disconnects every device), only used by Moblin's WebSocket and only leaving the backend in the signed in account, which the streamer pastes into the global Moblin Cloud settings of up to 5 devices running Moblin; Moblin connects to `/remote-control/streamer/{key}` under its `MOBLIN_WEBSITE_API_URL`, separately from its own remote control. The page's public id is 12 random bytes in base64url (`Streamers::new_page_id`), unrelated to the key, and stays when the key is replaced. A device is told apart by the `streamerId` of its `identify` message (Moblin's per install id): one without it is refused (`moblinConnectionsFailed:no-device-id`), as is a sixth device of a page (`too-many-devices`), both answered `identified` with an `error` result (Moblin shows "Failed to identify" and keeps retrying) before the socket is closed (`remote_control::refuse`), while a device connecting again replaces its old session. Remote control sessions are per page and device, in the order they connected: song requests (`find`, `status`, `songRequests`) use the page's music device, the first connected device with song requests on in Moblin's Moblin Cloud settings (else the first one), wheel spins its wheel device, the first with a wheel picked there (else the first one), and tips go to every connected device; the settings' `connected` is whether any device is. The signed in account's `devices` lists the connected ones with their `name` (`Moblin <number>` with the smallest number no other device of the page is named with, given when the page first sees it, or the name the streamer gave it with `POST /account/devices/{device}/name`, 1 to 30 characters; `Accounts::seen_device` and `rename_device` in the `devices` table, keyed by the account and the `streamerId`, forgotten with its name after 30 days unseen and at most 20 kept per account, a new one replacing the one seen longest ago; the dashboard renames connected devices only) and whether each is the `music` or `wheel` device, which the dashboard's Moblin section shows. Song orders and their captures share the same checks (`song_and_user`, then `requested_song`, which asks Moblin to `find` the song); song orders are refused with 429 past 10 a minute per page (`Api::song_finds`, in memory, checked before `find` so viewers can't flood the streamer's Moblin); a completed capture queues the song (`record_capture`), answering 202. Song requests and spins without a payment are only those of Twitch subscribers (`subscribers.rs`) and the streamer's own tests. Tips need no connected streamer; a completed tip capture queues the tip (`deliveries.rs`) for Moblin. Wheel spins need Moblin's wheel (`wheel`, so a connected streamer that sent one) both to create an order and to capture it; a completed spin capture queues the spins the same way. Order requests take an optional `provider` (`paypal`, the default, or `stripe`), the public song, tip and spin answers carry the PayPal fields and `stripe` (publishable key and connected account) for whichever the streamer connected, and a Stripe order also answers its `clientSecret`. Song, tip and spin orders share `capture_order`, which refuses an order of another kind (`Item::kind`), and cancels a Stripe payment it refuses because the streamer or the wheel is gone, so the hold on the viewer's card is released. A capture moves the order through the stages in `payments.rs`: `created` to `capturing` before the provider is asked (a database that cannot be written refuses the capture with 503 `not-saved` before any money moves; two captures at once are harmless, since the provider answers the second one already captured and `record_capture` saves a capture once), then `captured` together with its delivery in one transaction (`record_capture`), back to `created` when the provider refused or the viewer had not approved, and still `capturing` while the provider reviews it, so `capturing` means the money may have been taken and only the provider can tell. When the provider's answer is lost (a transport error, a 5xx or an unreadable body, `CaptureError::Unknown`), the capture handler looks the order up at the provider at once (`settle_one`) and only answers 502 `unknown` ("did not answer. If the money was taken, the tip will still be shown.") when the lookup fails too; a retried capture of a capturing order looks it up again, and a captured one answers 202 again, so the page retries a capture on network errors and 5xx answers (three times) without ever showing an error for a payment that went through. `settle_orders` is a background task that, every minute, looks up every capturing order older than a minute (`PayPal::status`, `Stripe::status`) and queues the delivery of those the provider captured, so a pending review that completes days later, a capture whose answer was lost or a crash between the provider's answer and the database still deliver. The `/account/test/*` routes let the signed in streamer send themselves a free song, tip or wheel spin from the dashboard's Tips, Wheel of luck and Song requests sections, to check that Moblin gets them: they skip payment and need no PayPal or Stripe, but run the same Moblin checks as paid ones (`requested_song` for songs, the wheel for spins, nothing for tips, which wait in the queue for Moblin like paid tips), so songs and spins are refused with 409 `Connect Moblin first.` without a connected device; all are refused with 429 past 10 tests a minute per page (`Api::tests`, in memory), and queue a delivery under the account's name with the first suggested tip amount (5.00 without tips) or the first spin option's spins (1 without a wheel option). `GET /account/recent?kind=<song|tip|spin>` pages through the signed in streamer's captured orders of that kind, newest first (`Orders::recent`, by the `kind` column and the `orders_recent` index; captured orders are kept 30 days, so that is the whole history), `limit` of them (20 by default, at most 50) `before` the order id given, answering `items` and whether there are `more`; test deliveries are not listed. A paid item has its `provider` (`paypal` or `stripe`), only in the streamer's own list, never in a moderator's (`GET /account/pages/{id}/recent`). Each item has its `status`: `delivered` when its delivery is finished (or no delivery row is left), `waiting` while Moblin has not got it, `notAdded` when Moblin could not find the song, and its `devices` with whether each `received` it (a finished delivery lists only the devices that got it, an unfinished one also the connected ones it still waits for: every connected device for a tip, the music device for a song and the wheel device for a spin), which the dashboard shows in place of a status, except `notAdded` and `waiting` with no device listed ("Waiting for Moblin"). The dashboard shows each kind under its section's test card (`Latest` and `createRecent` in `components/Latest.tsx`): the first 5 when the dashboard opens, then 20 more per Show more, refreshed every 30 s while the tab is visible (the shown ones, at most 50; older loaded ones are kept), each item with a Send again button (`POST /account/recent/{order}/resend`, or `/account/pages/{id}/recent/{order}/resend` for a moderator) that queues the captured order's delivery again (`Deliveries::resend`: the delivery row is reset, or inserted when it was pruned, with `resends` bumped, so Moblin gets it under a new `requestId` of `<order id>-<resends>` and its dedup does not swallow it; it then shows as `waiting` until Moblin gets it). Viewer-facing errors are full sentences the page shows as they are. `GET /admin/stats` is for the site operator: the Twitch user ids, or `kick:<Kick user id>`, in `--admins` (env `ADMINS`, comma separated) are admins (an account is an admin when any of its identities is listed, `Identity::admin_key`), `GET /account` answers `admin` for them and everyone else gets 403; it answers counts of accounts (total, PayPal and Stripe connected, and premium: signed in admins and `--premium-accounts`), connected devices (`connected_count`, every session of every page), unfinished orders and pending deliveries that no device has received yet (a tip some of the page's devices got is not pending; plain column counts, no JSON is read), the SQLite database size in bytes (`database`: the main, `-wal` and `-shm` files on disk, 0 in memory), the `server`: its `version` (the release tag, passed to the Docker build as `VERSION` by the deploy workflow and compiled in as `MOBLIN_WEBSITE_VERSION`, `dev` otherwise), when it `started` and the server's `now` (unix seconds, for the uptime), its resident `memory` (from `/proc/self/status`, null off Linux) and which `integrations` are configured (Twitch, Kick, App Attest, PayPal, Stripe), plus the event `counters` (`counters.rs`); unfinished orders are those not yet captured. CORS allows only `https://moblin.app` (hardcoded).
- `subscribers.rs` — song requests and wheel spins for Twitch and Kick subscribers without a payment, each on with its page setting, `subSongs` and `subSpins` (`pages::Tiers`, 0 to 100 songs or spins a month per tier with at least one above 0, whatever a song's length; neither needs PayPal or Stripe, and each works with or without its paid feature). Both need the page's account to have a Twitch or Kick identity linked: without either the public answers show them as null and the checks treat them as off (`sub_tiers`), whatever the settings say, and a viewer sign in with a platform the page has not linked answers 404. A viewer signs in with `GET /auth/twitch/login?page=<id>` (scope `user:read:subscriptions`, the page kept with the state) or `GET /auth/kick/login?page=<id>` (the normal Kick scopes); the Twitch callback asks Helix `subscriptions/user` for their tier to the page's streamer (`Auth::twitch_subscription_tier`, the Twitch user id of the page's account's Twitch identity), and the Kick callback asks Kick's website API `GET https://kick.com/api/v2/channels/{streamer slug}/users/{viewer slug}` (`Auth::kick_subscriber`, `KickApp::channel_users_url`, the same unofficial API `kick.rs` uses; the slugs are the identities' logins, the viewer's from the official channels API at sign in) for an active `subscriber` badge, which gives tier 1, so Kick subscribers get the tier 1 allowance. Neither creates an account; both redirect to the page under the login of the viewer's platform (`/twitch/<login>` or `/kick/<slug>`, falling back to any linked one) with `#viewer=<token>`, `#viewerSignInFailed=<platform>` when the sign in failed, or `#viewerCheckFailed` when the Kick badge check failed (a transport error or an error status), in which case the page says "Couldn't check your Kick subscription, try again." and nothing is granted. The viewer token (`Auth::viewer_session`, `viewer_of`) is HMAC signed like a session but prefixed `viewer:` so neither is accepted as the other, holds the `platform` (Twitch for tokens from before), user id, name, page and tier, and lasts 24 hours since the tier is a snapshot; a token whose platform the page no longer has linked is refused with 401 (`viewer`). Allowances are keyed by `Viewer::key`, the Twitch user id or `kick:<Kick user id>`, so the two platforms' numeric ids never collide. `GET /pages/{id}/songs/subscriber` and `GET /pages/{id}/spin/subscriber` answer the viewer's `platform`, `name`, `tier`, `allowance` and `left`. `POST /pages/{id}/songs/subscriber` (`song`, `message`) runs the same Moblin checks as a paid song (`song_and_user` with the viewer's name as the user, the `song_finds` limit, `requested_song`); `POST /pages/{id}/spin/subscriber` (`message`) spins once and needs Moblin's wheel like a paid spin (`wheel_available`). Both (`subscriber`, then `queue_for_subscriber`) count in one transaction (`Allowances::take`) in the `subscriber_allowances` table (per page, viewer key, kind and UTC month, so it resets on the 1st; past months are pruned), save a captured order with `Payee::Twitch(tier)` or `Payee::Kick` and price 0 (so it shows in `GET /account/recent` with its `tier`, or `kickSubscriber`) and queue its delivery like a paid one, answering 202 with `left`. Lowering a tier mid-month leaves 0, raising it gives the extra at once. Counted as `subSongs` and `subSpins`. With the fake Twitch the tier is the trailing digit of the fake login (`sub1` to `sub3`, otherwise not subscribed); with the fake Kick a login ending in 1 to 3 is a subscriber. The page offers a sign in button per linked platform (`SubscriberBox` in `pages/Page.tsx`, from the public page's `twitch` and `kick`), and the dashboard's subscriber cards show only the tier 1 field, as "Kick subscribers", when only Kick is linked.
- Moderators (in `api/moderators.rs`, stored by `accounts.rs`) — an allow list per platform the streamer keeps by hand in the dashboard's Moderators section, which shows a list with a username form for each linked platform; Moblin Cloud never asks Twitch or Kick who moderates a channel. `POST /account/moderators/{platform}` with `username` (409 `Link Twitch first.` or `Link Kick first.` without that identity, 404 `no such platform` for any other platform) resolves the username to a user id, with Helix `GET /helix/users?login=<username>` under an app access token (client credentials at the token URL, `Auth::twitch_user`) for Twitch or the official `GET https://api.kick.com/public/v1/channels?slug=<username>` under an app access token (`Auth::kick_user`) for Kick (both through `Auth::user`; 400 `Enter a Twitch username.` for a username that can't be one, 404 `There is no Twitch user named <username>.` when the platform lists none, 502 `Couldn't look the Twitch user up. Try again.` when the lookup fails, 409 `That is your own Twitch account.` for the streamer's own account, 409 `at most 50 moderators` per platform) and saves it with the login and name at the time in the `twitch_moderators` or `kick_moderators` table (`moderators_table`; broadcaster's and moderator's user ids on that platform, `Accounts::add_moderator`), so a rename changes nothing about who has access; `POST /account/moderators/{platform}/{moderator}/remove` (the user id) drops the row and takes effect at once (404 `no such moderator` when not listed). Both answer the account. The tables hold platform user ids on both sides, never account ids, and are resolved to accounts through the `identities` table (`Accounts::moderated`, `moderates`), so an account without that platform has no moderators on it, and a channel's list survives unlinking and relinking it. `GET /account` answers `twitchModerators` and `kickModerators` (`Accounts::moderators`, each with the `id`, and the login and name of their identity when they have signed in to Moblin Cloud, else the ones resolved when added) and `moderating`, the channels the user moderates (each with the `platform` they moderate through and the name, login and avatar of the channel's identity on it, plus the channel's `twitch` and `kick` identities, null when not linked, so the dashboard opens a channel under either of its logins); a moderator moderates a page when their identity's user id on a platform is listed under the page's account's user id on that platform (`moderator()` checks both platforms). Deleting an account removes its moderator rows in both directions on every linked platform. The routes take the normal session and are allowed for the page's own account or one of its moderators (`moderator()`, 403 `not-moderator`): `POST /account/pages/{id}/music` (`command`: `play`, `pause`, `clear`, `remove` or `select` with the queue entry's `id`) sends Moblin's music command to the music device and answers the queue like `GET /pages/{id}/songs/queue`; `POST /account/pages/{id}/songs` (`song`, `message`) adds a song for free with the paid song's Moblin checks, saved as a captured order with `Payee::Moderator` and price 0 (listed in recent with `moderator`) and delivered like a paid one; `GET /account/pages/{id}/recent` answers what `GET /account/recent` answers the streamer, and `POST /account/pages/{id}/recent/{order}/resend` sends an item again like the streamer's. A moderator gets the streamer's dashboard: `GET /account/pages/{id}` answers the page's account like `GET /account` but without payments (`without_payments`: `paypal` and `stripe` false, no merchant or Stripe account id, nothing pending) and with no `devices`, `moderators` or `moderating`, `admin` false and the streamer's `premium`; `POST /account/pages/{id}/settings` saves the look, subscriber tiers, longest song, paid songs, tips and wheel like the streamer's `POST /account/settings` (so turning a paid feature on or changing its amounts needs the streamer's PayPal or Stripe connected, 409 otherwise) but keeps the page's currency whatever the request says (`handle_moderator_settings`), `POST /account/pages/{id}/image` and `/image/remove` change the banner (premium by the streamer, counted as `imageUploads`) and `POST /account/pages/{id}/test/tip` and `/test/spin` send the moderator's own test tip or spin like the streamer's `/account/test/*` (same limit and counters, under the moderator's name). The dashboard (`Admin` in `pages/Dashboard.tsx`) has a Streamer picker at the top for anyone who moderates a channel (the picked channel kept per tab in the URL as `/dashboard/<platform>/<login>`, matched against either of the channel's logins, so each tab can show its own streamer and be bookmarked, with `sessionStorage` as the fallback when the URL has none; "You" for their own page); picking a channel shows that streamer's dashboard (`Moderated` fetches the page's account, then `Admin` with `page` set, whose calls in `data/account.ts` go to the `/account/pages/{id}` routes) without the Payments, Moderators and Moblin sections, with the same price settings as the streamer (the needs-payments card tells a moderator the streamer has to connect PayPal or Stripe; the settings' `payable`, kept by `without_payments`, is whether the page can take payments, which the dashboard uses in place of the merchant and Stripe account ids), and with the free song form (`FreeSong`) in place of the test song. The streamer and the moderator both get the queue with play/pause, clear and per song play now and remove (`MusicQueue`, the `Player` in `components/Player.tsx`, shared with the tip page: the played songs in a scroll view above the now playing block, hidden until Show history is pressed and scrolled to the latest, and the coming ones listed in full below it, all numbered by their place in Moblin's playlist) in Song requests. Counted as `modSongs` and `moderatorMusic`. With the fake Twitch and the fake Kick, any login resolves to a user (except `nobody`).
- `images.rs` — the banner image of a page. Only premium accounts (the Twitch user ids, or `kick:<Kick user id>`, in `--premium-accounts`, env `PREMIUM_ACCOUNTS`, matched against any linked identity, plus admins; `GET /account` answers `premium`) may upload one, with `POST /account/image` (the file as the raw body, at most 2 MB), which the dashboard's Tip page section shows to them only. `banner` decodes a JPEG, PNG, WebP or GIF of at least 600 pixels wide and at most 4000 pixels on each side, crops it to 3:1 around the center and re-encodes it as a 1500×500 JPEG, so nothing but pixels is kept; it is saved in the `page_images` table with a version (a hash of it), answered as `image` with the page's settings and look, and served by `GET /pages/{id}/image?v=<version>` with a year long immutable cache. Counted as `imageUploads`. `POST /account/image/remove` works for everyone, and taking a streamer off `--premium-accounts` only stops new uploads; the operator deletes the row to take one down.
- `store.rs` — list of streamers, newest post first, kept in memory and saved in the `streamers` table on every change (one row per streamer, its channels with their profile, live flag and stream as JSON), so it survives restarts; pending lookups start over and the live check runs a minute after starting. It keeps the `--max-streamers` most recent posters (so a newcomer is still around when the live check runs a minute later) plus any older streamer who is still live, up to another `--max-streamers`; `streamers()` lists live streamers first, capped at `--max-streamers`. A streamer is identified by sharing any channel (platform + case-insensitive name); going live again moves to the top and keeps any already-looked-up profile and the live flag. Each listed channel carries a `Lookup` (pending with retry backoff, or done) that serializes flat into the channel JSON as `avatar`/`displayName`, plus `live` (only ever true for Twitch and Kick channels).
- `profiles.rs` — a background task that pulls the next due lookup from the store and resolves display name and avatar per platform (Twitch via Helix, YouTube via `og:` meta tags with unavatar.io fallback, Kick via `kick.rs`, its public channels API), with `--lookup-spacing` between requests.
- `app_attest.rs` — verifies Apple App Attest attestations and assertions so only the Moblin app can post live. Stateless by design: the app resends its attestation every time and the server re-verifies the chain each time, deliberately ignoring certificate validity dates. Tests use public sample vectors in `src/testdata/`.
- `challenges.rs` — one-time 32-byte challenges, 120 s lifetime, that every live post must consume.
- `remote_control.rs` — the assistant side of Moblin's remote control protocol, for song requests on the page. Moblin Cloud connects with the key in the URL and an empty password, which the backend does not check. Serde types mirror Swift's synthesized `Codable` (`{"ping":{}}`, optional fields omitted), and must match `Moblin/RemoteControl/RemoteControl.swift` in the Moblin repo. Moblin pushes its wheel (the wheel of luck widget picked in Moblin's Moblin Cloud settings) as a `wheelOfLuck` event on connect and on every change; it is kept with the session and served by `GET /pages/{id}/spin` as `wheel` for the page to draw, next to `connected`, so the page can tell a streamer who is offline from one who picked no wheel (whose spin orders are refused with 409). It also pushes `songRequests` (`enabled`, the Song requests toggle in the same settings) on connect and on every change; while it is off (it is on until Moblin says otherwise), song orders and song captures are refused with 409 and `GET /pages/{id}/songs/queue` answers `songRequests: false`, so the page says songs can't be added right now but still shows the queue. Requests sent are `spinWheelOfLuck` (viewer name, message, number of spins and `requestId`) and `tip` (viewer name, message, amount as a string like `7.00`, currency and `requestId`), both answered `ok` without data and deduplicated by Moblin on `requestId`, and `music`: `status`, `find` (is a song on the streamer's Apple Music, asked before payment) and `add` (with the viewer's optional `message`, which Moblin does not read yet, and an optional `requestId`, kept on the song in Moblin's playlist; Moblin answers `ok` without adding again when a playlist song already has it, and `error` when it could not add it). Song requests must be Apple Music song links, sent as `https://music.apple.com/song/<id>?i=<id>`.
- `database.rs` — the SQLite database (`rusqlite`, SQLite bundled) at `--database`, in memory without it, shared by `Store`, `Accounts`, `Pages`, `Orders`, `Deliveries` and `Counters` behind one mutex. Tables are created with `CREATE TABLE IF NOT EXISTS` on start; the only migration drops the old `devices` table with its per device keys, gives every account a new Moblin Cloud key in `accounts.moblin_key` and drops `music_device` and `wheel_device` (remove it once it has run), so otherwise a schema change needs the existing database changed by hand.
- `counters.rs` — event counters for the admin page, one row per name and UTC day in the `counters` table, read back as today, last 7 days and all time. Measurement points come in pairs, `<name>` for successes and `<name>Failed:<reason>` for failures, where the reason is the `reason` slug every `Failure` in the API carries (`counted` does the bumping), which the admin page lists as one plain row per reason under the success row, always showing the reasons each code path can produce (`failures` per event in `Admin.tsx`, labels in `reasonLabels`) plus any unexpected one that occurred: Moblin's WebSocket connecting with a known key or failing with an unknown key, no device id or more than 5 devices (`moblinConnections`), created orders and captured payments (`songOrders`, `songPayments` and so on per `Item::kind`, any refusal or provider error counting as failed), the same per provider (`paypalOrders`, `stripeOrders`, `paypalPayments`, `stripePayments` by `Payee::slug`: orders from the moment the provider is asked to create one in `start_order`, captures from the moment it is asked to capture in `capture_at_provider`, so the page's own refusals before that only count under the kind; a captured payment counts for its kind and its provider in the same transaction), songs and spins of Twitch subscribers (`subSongs`, `subSpins`), moderators' free songs and queue changes (`modSongs`, `moderatorMusic`), the dashboard's free test sends (`songTests`, `tipTests`, `spinTests`; their deliveries and expiries are counted as `songTestDeliveries`, `songTestExpiries` and so on, shown in their own Tests table and left out of the Problems), and in `deliveries.rs` a delivery that reached every device (`songDeliveries`, `tipDeliveries`, `spinDeliveries`) or that Moblin could not find or refused (`...DeliveriesFailed`, once per delivery and reason). The free `counters::bump` takes a connection, for callers already holding the database lock.
- `pages.rs` — per streamer page settings (`Pages`), keyed by the public id: the one currency of all its payments (USD by default, set in the dashboard's Payments section; changing it while a paid feature is on needs PayPal or Stripe connected), optional paid songs (`songs`, one price in hundredths for every song whatever its length, and songs always play in full; song requests are on exactly when it is on), an optional longest song (`maxSongLength` with its `minutes`, 1 to 60, on with 7 minutes for new accounts, whose settings row `Accounts` creates with the account; answered as `maxSongMinutes` by `GET /pages/{id}/songs`; paid and subscriber songs whose duration from Moblin's `find` is longer are refused with 422 `over-max-length`, moderators' songs and the streamer's tests are not), optional tips (one to five suggested amounts in hundredths), an optional spin wheel (one to five options of a number of spins and its price) each of the paid songs, tips, wheel, subscriber tiers and longest song a `Feature` with an `enabled` flag next to its values, so turning one off keeps its values for when it is turned on again (`enabled` defaults to true, so settings saved before the flag are on; the checks and the public answers only see features that are on, through `Settings::songs()` and the like, and the public answers show one that is off as null) and the look of the page (message up to 300 characters, accent color from a fixed list whose CSS lives in `index.css` as `[data-accent]` overrides of the moss/leaf tokens, or for premium accounts any `#rrggbb` color, drawn as `[data-accent="custom"]` with the color in `--accent` (`accentAttributes`; a streamer taken off `--premium-accounts` keeps theirs but can't pick a new one), and, for premium accounts, a font from a fixed list (refused with 403 for others, who likewise keep one picked while premium), `[data-font]` overrides of `--font-display`/`--font-body` whose Google Fonts `loadFonts` adds only when used). `GET /pages/{id}` returns the look with the name, avatar and banner image version (`images.rs`). Saved as JSON in the `pages` table on every change.
- `auth.rs` — streamer sign in with Twitch (OAuth authorization code, `OAuthApp`) or Kick (OAuth authorization code with PKCE S256, `KickApp`: authorize at `https://id.kick.com/oauth/authorize`, token at `https://id.kick.com/oauth/token` with the `code_verifier` kept with the state, scopes `user:read channel:read`, the user from `GET https://api.kick.com/public/v1/users` and the login from the channel `slug` of `GET https://api.kick.com/public/v1/channels`, both answered for the token's own user; the Kick user id is a number, read as text; `--kick-client-id` and `--kick-client-secret`, env `KICK_CLIENT_ID` and `KICK_CLIENT_SECRET`, without which `GET /auth/kick/login` answers 503), each callback giving an `Identity` (platform, user id, lowercase login, name, avatar), with one-time states (`SignInState`: the viewer's page, whether it is a link and the PKCE verifier) that last 10 minutes and must match the `moblin_sign_in_state` cookie set by `GET /auth/<platform>/login`, so a callback URL only works in the browser that started the sign in. `signed_in_redirect` in `api/sign_in.rs` handles both platforms: a normal sign in finds the account of the identity (`Accounts::signed_in`) or creates one with a random id and a new page, and redirects to `/dashboard/#session=<token>`; `?link=1` on the login route makes a link flow, whose callback does not touch any account but redirects to `/account/#link=<link token>` (`#linkFailed` when it failed), a signed token prefixed `link:` holding the identity for 10 minutes (`Auth::link_token`, `link_of`), which the Account page posts to `POST /account/link` with its session, so the identity is linked to the account whose browser finished the flow and a callback link handed to someone else links their own identity to their own account; `POST /account/unlink/{platform}` removes a linked identity, 409 for the last one. Sessions are `<account id>:<generation>:<issued>` signed with HMAC-SHA256 under `--session-secret` (random without it), 30 days, sent as a bearer token (`signed_in` in `api.rs` also accepts a session whose account id is a Twitch user id, from before the ids were renamed, by looking the account up through its Twitch identity, so renaming signed nobody out); viewer (`viewer:`) and link (`link:`) tokens are signed the same way and none is accepted as another. A session is only accepted while its generation matches the account's `sessions` counter, which signing out increments; starting to connect PayPal (`POST /account/paypal/connect`) needs a session issued in the last 10 minutes. The Twitch and Kick URLs are fields of `OAuthApp` and `KickApp` so tests can point them at a local server.
- `accounts.rs` — one account per streamer, keyed by a random id of 32 hex characters (`Streamers::new_account_id` for new accounts, SQLite's `randomblob` for the ones renamed on start, see `database.rs`), with its linked identities in the `identities` table (`Identity`: `platform`, `twitch` or `kick`, `user_id`, `account`, `login`, `name`, `avatar`; primary key platform and user id, so a platform account belongs to one Moblin Cloud account), each giving the page an address, `/twitch/<login>` or `/kick/<login>` (`page_of_login` per platform; a login is unique per platform: it is taken from other identities on sign in, after renames, which leaves theirs empty). `signed_in` finds the identity's account or creates one (the account row with its key, its page's settings row and the identity in one transaction) and answers the id with the account; `link` adds an identity to an account and refuses one that belongs to another account (`IdentityTaken`, 409 "This Kick account already has its own page. Delete it first."; nothing is ever merged); `unlink` removes one and refuses the last (`LastIdentity`, 409). The account's name and avatar (`Account::name`, `avatar`, for the dashboard header, test sends and the Stripe account name) are those of its Twitch identity when it has one, else its Kick one; the pages show the identity of their address. Its page: a public id fixed at sign in, its Moblin Cloud key (`moblin_key`, uniquely indexed so the WebSocket route's `page_of_key` is an indexed lookup; `POST /account/key` replaces it and the WebSocket route only accepts the current key), and its PayPal: the merchant ID every paid feature of the page pays (`merchant_of`) and the tracking ID of an unfinished onboarding, and its Stripe connected account with whether it takes payments yet (`stripe_of`, only ready accounts). The merchant ID only ever comes from PayPal's seller onboarding (Partner Referrals): `POST /account/paypal/connect` creates a referral and answers PayPal's sign up link, and `POST /account/paypal/check` looks the tracking ID up with PayPal and connects the merchant ID once it can receive payments, has a confirmed email and granted our app third-party permissions; the return URL's parameters are never trusted. `POST /paypal/webhooks` (verified with PayPal's verify webhook signature API under `--paypal-webhook-id`) connects pending onboardings on `MERCHANT.ONBOARDING.COMPLETED` through the same `finish_onboarding` checks and disconnects merchants on `MERCHANT.PARTNER-CONSENT.REVOKED`; `POST /account/paypal/disconnect` forgets the merchant ID and any unfinished onboarding. Paid features can only be turned on or changed while PayPal or Stripe is connected. Saved in the `accounts` table. `POST /account/delete` (`Accounts::delete`, the Account page, with a confirm) removes the signed in account and everything it owns in one transaction: the account row, its identities, its devices, both directions of each identity's moderator rows, its page's settings, banner image, orders, deliveries and subscriber allowances; the handler then disconnects its Moblin devices, and signing in again starts a new account with a new page id. PayPal and Stripe accounts are never touched.
- `paypal.rs` — PayPal partner client: seller onboarding (`referral`, `seller`, which need the partner's merchant ID `--paypal-partner-id`; `--paypal-attribution-id` is the BN code sent with every request), webhook verification and Orders v2, created and captured for the streamer with an unsigned `PayPal-Auth-Assertion` JWT naming their merchant ID, for paid song requests, tips and wheel spins (an order's `Item` is a song, a tip with its message or a spin purchase with its number of spins and message): orders name the streamer's PayPal merchant ID as payee so money goes straight to them (never the email: PayPal no longer accepts emails as the SDK's `merchant-id`, and it would be public). A completed capture whose amount matches queues the song; a pending one (PayPal still reviewing it) is settled later by `settle_orders`, which asks `status` (GET the order).
- `stripe.rs` — Stripe Connect platform client, the alternative to PayPal. Streamers get a connected account (Accounts v2 API, full Stripe Dashboard, Stripe collects fees and losses) created on the first `POST /account/stripe/connect` in the country the streamer picks (`stripe::COUNTRIES`, the countries Stripe takes sign ups from, also listed in the frontend; Stripe can't change it later), which answers a Stripe-hosted onboarding link back to `/dashboard/?stripe`; `POST /account/stripe/check` marks it ready once its `card_payments` capability is active. Payments are direct charges on the connected account (`Stripe-Account` header): a PaymentIntent (v1 API) with `capture_method=manual`, no redirect payment methods and no application fee, confirmed in the browser with the client secret and captured by the backend, like a PayPal order. On the page, "Pay with Stripe" creates the order first (so the viewer sees the final price, which for songs depends on the song) and then shows Stripe's Payment Element; changing the form closes it. `status` (GET the PaymentIntent) settles payments whose capture answer was lost. There are no Stripe webhooks; a revoked account only fails new payments until the streamer checks again. `--stripe-secret-key` and `--stripe-publishable-key`; a test mode key takes test payments.
- `payments.rs` — what is provider neutral about payments: the order (`Item`, `Order` with its `Payee`, a PayPal merchant ID, a Stripe account or `Twitch` with the tier of a subscriber's song or spin or `Moderator` for a moderator's free song, both saved already captured and never reaching a provider, and its description), `CaptureError` (`NotApproved`, `AlreadyCaptured`, `Pending`, `Refused` when the provider definitely said no, `Unknown` when its answer was lost), `PaymentStatus` (what a lookup at the provider says: captured, pending, not captured or gone) and `Orders`, every order in the `orders` table with its `Stage` (`created`, `capturing`, `captured`) and the order as JSON, so a restart loses no payment: `start_order` inserts after creating the provider's order (refusing the order with 503 `not-saved` if that fails), `transition` is a compare-and-set between stages, `captured` runs the stage change and the delivery insert in one transaction, `unsettled` lists the capturing orders older than a given age for `settle_orders`, `expire` drops created orders after three hours (`settle_orders` then cancels their Stripe payments, so a viewer whose capture never reached the backend gets the hold on their card released), `make_room` refuses new ones past 10000 unfinished, `captured` does nothing for an order already captured and otherwise counts `<kind>Payments` in the same transaction as the delivery, so a payment is counted once however it was found, and `prune` gives unsettled orders up and forgets captured ones after 30 days.
- `deliveries.rs` — at least once delivery to Moblin of paid songs, tips and wheel spins, saved in the `deliveries` table. Deliveries are kept per page and their devices picked among the page's connected ones when delivering: songs go to the music device, spins to the wheel device and tips to every connected device, tracked in `delivered` (by `streamerId`) so each device gets a tip once; a tip is finished once a device got it and every device connected then has it, so a device connecting while a tip waits gets it too. A delivery every device got is marked `finished` and kept 30 days, so the dashboard can tell which devices got a tip. Test deliveries (`add_test`) are marked with their kind in `test`, and only the 5 newest per page and kind are kept. A background task delivers them whenever a device connects, after a request and every 10 s, each connected device concurrently, by sending `add`, `tip` or `spinWheelOfLuck` with the request id (random, or the PayPal order id) as `requestId` until Moblin answers `ok`; Moblin's own dedup on `requestId` makes the retries safe. A song request is always delivered as a song, never as anything else. A song Moblin answers it can't find (`songNotFound`) is final: the delivery stays in the table with `failure` set to `not-found`, is not sent again, shows as `notAdded` on the dashboard so the streamer can add it by hand or refund, and is forgotten after 30 days. Any other Moblin `error` (Apple Music not authorized, playlist not loaded, a failed search) is temporary and retried; `failure` records the latest reason so each failure is counted once per delivery and reason. A delivery waits in the table until a device gets it and is only given up after 7 days (the one way a paid request is allowed to fail), counted as `songExpiries`, `tipExpiries` or `spinExpiries` when no device got it.
- `twitch.rs` / `live.rs` / `live_status.rs` — Helix client with a cached app access token; a once-per-minute cache of whether the featured channel is live; and a background task that checks which listed channels are live every five minutes and one minute after a live post: all Twitch channels in one streams request, Kick channels one by one with `--lookup-spacing` between them.

Everything optional degrades rather than fails: without Twitch credentials, Twitch profiles come back empty and `/twitch/live` answers 503; without Kick credentials, Kick sign in answers 503. `--allow-unattested` disables App Attest, `--twitch-sign-in-url <base>` points the sign in's OAuth and Helix endpoints (`OAuthApp::at`) at another server and `--kick-sign-in-url <base>` Kick's (`KickApp::at`, including the website API's `channel_users_url` the subscriber check uses), with no client ID or secret needed, both for local development and the system tests only. There is no fake logic in the backend: the fake Twitch is `tests/utils/fake_twitch.py` (stdlib only), an HTTP server whose authorize page lets the browser pick any made-up login (or takes it as `login` in the query, which the system tests do), whose user id is `fake-<login>`, with a login ending in 1 to 3 subscribed at that tier to everyone and any login but `nobody` resolved by its users endpoint under an app access token (client credentials); the fake Kick is `tests/utils/fake_kick.py`, the same for Kick's OAuth (checking the PKCE challenge, with client credentials for the username lookup), public API (also by `slug`) and the website API's channel user (a login ending in 1 to 3 has a subscriber badge), whose user id is `fake-<login>` too, so the same login on both fakes is two different users until linked. `just backend-run` starts them on ports 8081 and 8082 and passes both options, with `--admins fake-admin,kick:fake-admin` making `admin` an admin, and so premium, on both and `--premium-accounts fake-premium,kick:fake-premium` making `premium` a premium account; `normal` is neither. The system tests start both on free ports when `[twitch] sign-in` is `fake` (`Backend.fake_twitch`, `Backend.fake_kick`).

## Conventions

- **Do not write comments or docstrings.**
- **Magic numbers are fine, and often preferred, when used in a single place.** Do not hoist a literal
  into a named constant just because it is a literal — only name it when the same value is used in more
  than one place.
- Rust edition 2024 (let-chains are used). Clippy warnings are errors in CI.
- The `/streamers/live` request shape (`channels`, `challenge`, `keyId`, `attestation`, `attestationChallenge`, header `moblin-assertion`) is a contract with the Moblin iOS app; changing it requires an app change too.
- Streamers appear in the list only if they opted in inside the Moblin app. Site copy must not imply that everyone who goes live is listed.

## Reporting

- Never mention styling or formatting changes (oxfmt, cargo fmt output) in summaries, reviews or commit
  messages.
